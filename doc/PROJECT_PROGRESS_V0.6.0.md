## 1. 本期结论

V0.5.0 把编辑器与 Agent 之间接成了一条闭环：用户挑上下文 → Agent 提改动 → 编辑器按文件/按块批准或拒绝 → 冲突交给用户选 → 每一环可追溯。

这一期补另一半：**编辑器自己也要像个开发工具**。现在它能读文件、能高亮、能补全、能跑 Agent，但「改代码」这件事仍主要靠人：格式化要另开终端跑 `cargo fmt`，重命名要全局搜索加手改，跑程序要另开一个控制台。

本期做四件事：

1. **集成终端与任务运行器**（DF-0601）：编辑器里能跑命令、看得见输出、失败时看得见原因。
2. **Git 状态、Diff、暂存与提交**（DF-0602）：改了什么、暂存什么、提交什么，都在编辑器里看得见、点得动。
3. **LSP 格式化、重命名、代码操作**（DF-0603 / DF-0604 / DF-0605）：语言服务器会的事，编辑器里按一下键就能用。
4. **最小 DAP 调试能力**（DF-0606）：断点、单步、看变量。
5. **全局搜索**（DF-0608）：在工程的文件里找文字，找到的地方点得开。
6. **交互式终端**（DF-0610）：`Ctrl+Shift+T` 开一个长住的 shell，键盘有焦点，命令敲进去回车就跑，shell 一直活着。
7. **条件断点**（DF-0611）：`Ctrl+F9` 给断点写个条件，程序到了那一行、条件成立才停。
8. **调试表达式求值**（DF-0612）：`Ctrl+Shift+E` 问一个表达式，程序停住的时候答案回到调试面板里。
9. **在工程的文件里替换**（DF-0613）：`Ctrl+Shift+H` 打开查找并替换，找到的地方一处不落地换掉。
10. **调试面板的调用栈**（DF-0614）：停住的时候整条调用栈摆在面板左边，点哪一帧就切到哪一帧，变量跟着换。

本期先落第三块与第二块：**DF-0603 LSP 格式化**、**DF-0604 LSP 重命名**、**DF-0605 LSP 代码操作**——语言服务器会的事，在编辑器里按一下键就能用；格式化与重命中的改动都是**一次**事务，撤销一次整体回退。加上 **DF-0602 Git 改动面板**（`Ctrl+Shift+G` 打开：改了什么、差在哪、暂存、提交，都看得见、点得动）与 **DF-0606 最小 DAP 调试**（`F9` 断点、`F5` 开始、`F10`/`F11` 单步、顶帧的变量摆在面板里）。再加 **DF-0608 全局搜索**（`Ctrl+Shift+F` 打开：在工程的文件里找字，找到的地方列出来，挑一个就打开那个文件并把光标放到那一行；搜索跑在自己的线程上，工程再大窗口也不卡）与 **DF-0610 交互式终端**（`Ctrl+Shift+T` 打开：终端是一个长住的 shell，键盘焦点在终端上，敲进去的命令回车就跑，跑完 shell 还在接着跑；`Esc` 把键盘还给编辑器，shell 继续跑）。再加 **DF-0611 条件断点**（`Ctrl+F9` 打开：给这一行的断点写个条件，条件真的送到调试适配器，带条件的断点在正文边上换一种颜色）与 **DF-0612 调试表达式求值**（`Ctrl+Shift+E` 打开：程序停住的时候问一个表达式，适配器的答案回到调试面板里）。再加 **DF-0613 跨文件替换**（`Ctrl+Shift+H` 打开：多一栏「替换」，回车就把面板上列出的那些文件里的每一处都换掉）与 **DF-0614 调试面板的调用栈**（程序停住时整条栈摆在面板左栏，点哪一帧就切到哪一帧，变量与求值都跟着那一帧走）。

## 3. V0.6.0 开发项

### DF-0601 集成终端与任务运行器（进行中：实现完成，窗口验收待跑）

编辑器里能起一个任务、看得见它的输出、看得见它为什么失败。任务跑在**另起的进程**里：编辑器自己不被任务的死活牵连，编辑器关了，任务也停。

验收标准：

- `Ctrl+Shift+B` 起一次**构建任务**：命令按工程的清单来（`Cargo.toml` → `cargo build`，`package.json` → `npm run build`，`go.mod` → `go build`）；工程没有这些清单时，状态栏**明说**没有可以跑的命令，不静默什么都不发生。
- 任务的输出（标准输出与标准错误一起）流进窗口下方的输出面板，**一行一行**地出现，不是等它跑完才一下子冒出来。
- 任务失败时说得清：退出码是多少，输出里的最后几行是什么；输出面板自己标出「失败」。
- 任务在跑的时候再按一次键，不会起第二个任务：一次只跑一个。
- 输出面板可以关掉（`Esc`），关掉不影响任务继续跑。
- 任务的进程模型：另起的子进程，输出走管道，编辑器退出时任务被停掉。
- `Ctrl+Shift+P` 打开一个输入框写**任意命令**，回车就跑：命令在打开的文件所属的工程目录里跑，输出进同一个输出面板。跑过的命令**记在历史里**，输入框里按上下键就能翻出上一次的命令，再跑一遍不用重新打。
- 命令按 shell 的规矩拆开：空白分开算，引号里的算**一个**参数（`"C:\Program Files\x.exe"` 是一个整体）；引号没关上时状态栏**明说**命令写错了，不猜着跑。
- 命令是空的、没有工程（不知道在哪儿跑）、程序起不来时，状态栏**明说**原因，不静默什么都不发生。
- 输入框开着的时候它自己吃键：命令不会被敲进正文里，`Esc` 取消。

### DF-0602 Git 状态、Diff、暂存与提交（进行中：实现完成，窗口验收待跑）

改了什么、暂存什么、提交什么，都看得见、点得动。用**命令行 `git`**（机器上有 git 就够，不引第三方库），工程根目录由打开的文件往上找 `.git` 决定。

验收标准：

- `Ctrl+Shift+G` 打开「改动」面板：面板列出 git 知道改过的文件（`git status --porcelain`），每一个标着它的状态（改了 / 新增 / 没纳入版本管理 / 已暂存）。
- 选中一个文件时，面板把它的 diff（`git diff`）显示出来；已暂存的文件显示暂存区的那份（`git diff --cached`）。
- `S` 把选中的文件暂存起来（`git add`），面板立刻按新的状态重画——暂存这件事看得见，不靠猜。
- `C` 打开一个输入框写提交说明，回车后提交（`git commit -m`）；说明是空的时编辑器**明说**不能提交。
- 没有 git、没有仓库、命令失败时，编辑器在状态栏**明说**原因，不静默什么都不发生。
- 面板可以用 `Esc` 关掉；关掉不影响工程本身。
- git 模块的单元测试在一个真的临时仓库里跑：改一个文件 → 状态里有它 → 暂存 → 状态变了 → 提交 → 提交真的成了。

### DF-0603 LSP 格式化（进行中：实现完成，窗口验收待跑）

承接自 V0.5.0 的结转项：语言服务器会格式化，编辑器却用不上，只能另开终端跑 `cargo fmt`。这一期把它接进编辑器，作为 LSP 三件套（格式化、重命名、代码操作）的第一件。

验收标准：

- 编辑器能向语言服务器要一次格式化（`textDocument/formatting`），参数里带着当前文档的 URI、缩进设置与制表符宽度；请求的是**光标所在那个文件**，服务器看到的就是用户看到的文本。
- 服务器回来的每一段编辑（`TextEdit`）都以「文本编辑」应用，而不是整篇替换；多段编辑作为**一次**事务写进缓冲区：一次撤销整体回退。
- 格式化之后，文件被标记为已修改，编辑器把新文本告诉语言服务器（否则服务器手里的文档和用户眼前的不一致，后面的诊断全是错的）。
- 没有语言服务器、服务器断开、或者服务器不给出格式化结果时，编辑器在状态栏**明说**原因，不静默什么都不发生；「没有要改的地方」也要说出来，不能让人猜是不是没生效。
- 按键是 `Alt+Shift+F`（与 VS Code 一致；`Ctrl+Shift+F` 留给「在文件里查找」）。中文输入法下带修饰键的组合可能没有名字，按虚拟键码兜底。
- 协议形状、编辑应用、按键处理都有单元测试；窗口级验收脚本证明：按一次键，文件真的被重排了，撤销能整体回退。

### DF-0604 LSP 重命名（进行中：实现完成，窗口验收待跑）

重命名会改到别的文件里，涉及跨文件的编辑与冲突。它走 DF-0603 立起来的那条管道：发请求、收回答、把回答当成**一次**事务写进缓冲区。

验收标准：

- `F2` 打开一个输入框，里头是光标处那个名字；回车确认，`Esc` 取消。名字打错了不用等服务器回答就能改。
- 编辑器向语言服务器要一次重命名（`textDocument/rename`），参数里带着当前文档的 URI、光标所在的位置和新名字；请求的是**光标所在那个文件**，服务器看到的就是用户看到的文本。
- 服务器回来的编辑按文件分派：当前文件的编辑作为**一次**事务写进缓冲区（撤销一次整体回退）；别的文件如果在编辑器里开着，也作为一次事务写进那个缓冲区；没开着的文件，改动通过工作区服务写到磁盘，磁盘上被别人改过的文件不覆盖。
- 位置对不上的文件**整个不落**：重命名落在错的地方比不重命名更糟。
- 没有语言服务器、服务器断开、服务器说这个名字改不了时，编辑器在状态栏**明说**原因，不静默什么都不发生。
- 协议形状、编辑分派、按键处理都有单元测试；窗口级验收脚本证明：按一次 `F2`，改个名字回车，文件真的改了，撤销能整体回退。

### DF-0605 LSP 代码操作（进行中：实现完成，窗口验收待跑）

代码操作要有一个列表让人挑，界面得先有形状。它走 DF-0603 立起来的那条管道：发请求、收回答、把回答当成**一次**事务写进缓冲区。

验收标准：

- `Alt+Enter`（VS Code 的「上下文操作」键；`Ctrl+.` 已经用来取消 Agent 的一轮对话）向语言服务器要一次代码操作，参数里带着当前文档的 URI 与光标所在那一行的范围；请求的是**光标所在那个文件**。
- 服务器回来的操作列成一张表让人挑：上下键换，回车确认，`Esc` 取消。没挑之前什么都不改。
- 挑中的操作带着编辑时，那份编辑按 DF-0604 的办法落地：当前文件一次事务，别的文件按开没开着分别写进缓冲区或写到磁盘。
- 挑中的操作只带命令（不带编辑）时，编辑器把命令交给服务器执行，并把结果说明白，不假装什么都没发生。
- 没有语言服务器、服务器断开、服务器说这里没有可用的操作时，编辑器在状态栏**明说**原因。
- 协议形状、操作列表、按键处理都有单元测试。

### DF-0606 最小 DAP 调试能力（进行中：实现完成，窗口验收待跑）

调试要能断、能走、能看变量。走 Debug Adapter Protocol：适配器是外部程序，编辑器跟它说「断在第几行」「走一步」「给我这一帧的变量」，适配器把程序停下来、把变量说出来。

这一版只做**最小**的一套：断点、单步、顶帧的变量。

验收标准：

- 编辑器能起一个调试会话：调试适配器在命令行上点名（`--dap <program>`，跟 `--lsp` 一个路子）；适配器起不来、握手不成时，状态栏**明说**原因，不静默什么都不发生。
- `F9` 在光标那一行放/撤一个断点，行号左边画一个红点；断点按文件（URI）与行号记着，换了文件再回来还在。
- 握手是 DAP 的那套顺序：`initialize` → 适配器回 `initialized` → 每个文件一次 `setBreakpoints`（带上断点的行号）→ `configurationDone` → `launch`。顺序错了适配器自己会报错，编辑器把那句错话说出来。
- `F10`（步过）、`F11`（步入）、`Shift+F11`（步出）在暂停时发给适配器；适配器报「停住了」之后，编辑器**接着**问 `stackTrace` → `scopes` → `variables`，把顶帧的变量列在调试面板里。
- 调试面板在窗口下方：说清现在是什么状态（跑着 / 停住了 / 结束了）、适配器输出的内容（`output` 事件一行一行地来）、以及顶帧的变量名、值与类型。没有变量时**明说**「没有变量」，不画一块空白。（面板后来在左边加了整条调用栈、可以点帧切换，那是 DF-0614 补上的。）
- 调试结束时（`terminated` / `exited`）面板说清楚「调试结束了」，编辑器回到正常状态，不卡在一个半开的面板里。
- 协议形状、事件分发、单步的流程都有单元测试（对着一个**假适配器**跑，跟 LSP 的 `fake-lsp-server` 一个路子）；窗口级验收脚本证明：断点画出来了、面板里有变量。

### DF-0608 全局搜索（进行中：实现完成，窗口验收待跑）

在工程的文件里找文字：找到的地方列出来，挑一个就打开。这个键位是 DF-0603 的验收标准里**明文预留**的（`Ctrl+Shift+F` 留给「在文件里查找」）。

验收标准：

- `Ctrl+Shift+F` 打开「查找」面板：面板盖住窗口（它是人要用的东西，背后的正文不是他在看的东西），上头是输入框，下头是找到的地方（`路径:行号` 与那一行的文字）。
- 搜索**跑在自己的线程上**：工程大的时候窗口不卡住；面板在搜索期间说「正在找…」，结果到了才出现。搜索没找到时明说「没有找到」，不假装成功。
- 回车开始找；找到之后上下键挑地方，再回车打开那个文件、**把光标放到那一行**，面板关掉，状态栏说清打开了哪个文件的第几行。
- 搜的目录是**打开的文件所属的工程**（往上找工程的清单；没有清单就是文件自己所在的目录）；没有打开的文件时状态栏明说不知道在哪儿找。
- 找的规矩说清楚：构建产物目录（`target`、`node_modules`、`dist`…）不搜；不是文本的文件（二进制、不是 UTF-8）不读；**隐藏文件要搜**（`.github` 里的工作流也是工程的一部分）；字母大小写默认不算。
- 找到的地方太多时只留前面一千处，面板明说「太多了」，不假装只有这些。
- 输入框开着的时候它自己吃键：找的字不会被敲进正文里，`Esc` 关掉；上一次找的字留在框里，再找一次不用重打。
- 搜索与面板的单元测试分别在 workspace crate 与平台 crate 里；窗口级验收脚本证明：面板盖住窗口、字进了框、找到的地方列出来了、构建产物没被搜、挑中的地方真的打开了文件。

### DF-0609 断点跟着行数走（进行中：实现完成，窗口验收待跑）

文件改了行数之后，断点还停在原来的行号上——那一行已经不是它了。断点必须跟着它指着的那段文字走。

验收标准：

- 断点不只记着行号，还记着它在文字里的**位置**：在断点上面加一行，断点跟着往下走一行；在下面加一行，它不动；在它那一行里改字，它也不动。
- 撤销与重做一样跟着走：撤销把加的那一行拿走，断点回到原来那一行。
- 文件被关掉又打开：断点还在，新的地方照样跟着走（关掉的文件，它的「位置」随着缓冲区一起没了，重新打开时补上）。
- 断点动了以后，调试适配器要知道新的行号（`setBreakpoints`）——适配器不知道的断点不会让程序停下来。放/撤断点时也要告诉适配器。
- 撤掉断点时，它占的那个位置要还给缓冲区，不能一直挂着。
- 单元测试覆盖：断点跟着上面的文字走、下面的文字变了它不动、没打开的文件里的断点不动、撤掉断点时位置被放掉、文件重开后照样跟着走；窗口级验收脚本证明：正文左边的红点跟着往下挪了一行，撤销之后又挪回来。

### DF-0610 交互式终端（进行中：实现完成，窗口验收待跑）

编辑器里开一个**长住的 shell**：敲进去的命令回车就跑，跑完 shell 还在，接着敲下一条。键盘有焦点，敲的字进终端，不进正文。

这一项是 DF-0601 的延伸：任务运行器能跑命令，但跑完就没了；终端是那个「不结束的命令」。

验收标准：

- `Ctrl+Shift+T` 打开终端：终端是**长住的 shell**（Windows 上 `cmd.exe`，其它平台 `sh`），起在打开的文件所属的工程目录里；没有打开的文件时状态栏**明说**不知道在哪儿开终端，shell 起不来时**明说**原因。
- 键盘焦点在终端上：敲的字进终端，不进正文；带 `Ctrl`/`Alt` 的键**还给编辑器**（快捷键在哪儿都一样），终端**把键盘也还回去**——`Ctrl+F` 打开查找条之后，接着敲的字进的是查找条，不是终端。
- 回车把这一行写进 shell 的标准输入，shell 跑它，输出流进窗口下方的面板。
- shell 从管道读输入时**不回显**，编辑器自己把这一行回显进面板，顺序和 shell 说的话对得上。
- `Esc` 把键盘还给编辑器，**shell 继续跑**；`Ctrl+Shift+T` 把键盘拿回终端。键盘不在终端里时，那一行画得更暗、**没有光标**——人一眼能看出字打到哪里去了。
- 敲过的命令记在历史里，上下键翻出来，再跑一遍不用重打。
- 终端开着的时候构建任务（`Ctrl+Shift+B`）起不来，状态栏**明说**为什么（终端和任务共用一个面板位置），不静默什么都不发生。
- shell 自己退出时终端跟着关掉，状态栏说它关了；`Esc` 关面板时把 shell 也停掉——没人看着的 shell 没人能关。
- 单元测试：任务收得到写进去的输入、收输入的任务与不收输入的任务分得清、编辑器回显的行在任务说过的话里、终端开与关、`Esc` 还键盘、字不进正文、回车把行送进 shell、终端开着时构建任务起不来、按了快捷键终端就让出键盘；窗口级验收脚本证明：终端开着且光标在那一行、字进了终端没进正文、回车后 shell 的话在面板里、`Esc` 之后光标没了、`Ctrl+Shift+T` 之后光标又回来。

**取舍**：终端是**管道**而不是伪终端（PTY）。全屏程序（`vim`、`top`）在里面不工作，交互式的提示符也不回显。要真终端得在 Windows 上接 ConPTY，是后面的事。

### DF-0611 条件断点（进行中：实现完成，窗口验收待跑）

断点只有「到了这一行就停」这一种。要停在「这一行、而且满足某个条件」，就得给断点写个条件：`count > 3`——程序到了这一行，只有条件成立才停。

验收标准：

- `Ctrl+F9` 给光标所在行的断点写条件：编辑器问「条件是什么」，框里**先摆着这一行现在的条件**（改条件是改它，不是从零写）；这一行没有断点时状态栏**明说**「还没有断点」（`F9` 先放一个）。
- 条件写成空的就是**没有条件**：断点每次到这一行都停。条件是可以拿掉的。
- 条件跟着断点走：断点因为上面的行被加而往下挪时，条件跟着它挪；撤掉断点时条件也一起撤掉（条件属于断点）。
- 条件要**真的送到调试适配器**：`setBreakpoints` 的每个断点都带着自己的条件（协议里的 `condition` 字段）。适配器不知道的条件等于没有条件。
- 适配器对断点说的话要**显示在调试面板里**：它不认这个条件时，编辑器得说，而不是静默什么都不发生。
- 带条件的断点在正文边上画成**另一种颜色**（红的变成琥珀色）：它不是每次都停，人得一眼看出是哪一个。
- 单元测试：条件能记住、空条件等于没有条件、撤断点时条件跟着撤、条件跟着断点挪、这一行没有断点时明说、适配器真的收到了条件（契约测试对着仓库里的假适配器跑）；窗口级验收脚本证明：`Ctrl+F9` 写完条件之后，正文边上的断点换成了另一种颜色，而且它跟着断点一起挪。

**取舍**：编辑器**不检查**条件写得对不对——条件是**适配器**那边的语言（`debugpy` 里是 Python，别的适配器是别的语言），编辑器替它检查只会挡住合法的写法。仓库里的假适配器**不求值**条件，它只把条件记下来再回话：这样契约能验「条件到了适配器」，而「条件成立才停」这件事要靠真的适配器（`debugpy` 之类）验。

### DF-0612 调试表达式求值（进行中：实现完成，窗口验收待跑）

程序停住的时候，最想知道的是「这个变量现在是多少」。编辑器能问适配器：表达式是什么、值是多少。

验收标准：

- `Ctrl+Shift+E` 问一个表达式：编辑器弹出输入框，写的是程序**那个语言**的表达式（`count + 1` 在 Rust 里是加法，在别的语言里是别的意思——编辑器不替适配器解释它）。
- 程序**停住**的时候才能求值：还在跑的时候没有可求值的帧，状态栏**明说**「程序在跑，停下来才能求值」；没有调试会话时明说「没有调试会话」，不静默什么都不发生。
- 表达式要真的送到适配器（`evaluate` 请求），并且带上**它所在的那一帧的编号**：帧号是编辑器从 `stackTrace` 的应答里记下来的（适配器不知道编辑器问的是哪一帧）。
- 答案回到调试面板里：`表达式: 类型 = 值`（`count + 1: i32 = 42`）。适配器不认这个表达式时，编辑器**明说**求不了，不静默什么都不发生。
- 答案晚到也没关系：适配器在自己的线程上答，编辑器一帧一帧地收；表达式先记下来，答案来了才配上它（多个表达式在等的时候按问的顺序对）。
- 输入框开着的时候它自己吃键：表达式不会被敲进正文里，`Esc` 取消。
- 单元测试：协议层读得出答案（带类型、不带类型）、适配器不认的表达式是**错误**而不是空值、编辑器没有会话时明说、空表达式不问、输入框吃键；窗口级验收脚本证明：程序停住之后 `Ctrl+Shift+E` 写一个表达式，面板里多了一行答案。

**取舍**：仓库里的假适配器**不真的求值**——它对任何表达式都答 `42`，但它**看**表达式（空表达式它会拒），所以契约能验「表达式送到了适配器、答案读得回来」。真的求值要靠真的适配器（`debugpy` 之类）。

### DF-0613 在工程的文件里替换（进行中：实现完成，窗口验收待跑）

全局搜索找到了地方，却改不了：改一处要另开编辑器、逐个手改。这一项把「替换」补上。

验收标准：

- `Ctrl+Shift+H` 打开「查找并替换」面板：比查找面板多一栏「替换」，从上到下是「查找」「替换」「找到的地方」。
- `Tab` 在三栏之间轮转（查找 → 找到的地方 → 替换 → 查找）；在「替换」那一栏回车就是**全部替换**。
- 替换的规矩跟搜索一样：**字母大小写默认不算**——搜到 `Needle` 就换成新词，搜 `abc` 就把 `ABC` 也换掉。
- **开着**的文件改在缓冲区里，是**一次**事务：撤销一次整体回退；**没开着**的文件直接写进磁盘——**撤销不回来**（这跟语言服务器的重命名是同一个取舍，要说清楚）。
- 改的是**现在的**文字，不是搜索时的那一份：搜索之后文件被人动过，编辑器在现在的文字里重新找一遍，找不到就不动那个文件——**宁可不改，也不改错地方**。
- 折叠后长度会变的大小写字母（比如 `İ`）不做替换：那种情况下「位置」对不上，编辑器**明说**这个文件没敢改。
- 替换完了编辑器**明说**改了几个文件里的几处（有多少文件没改也说），然后**重新找一遍**：列表里是现在的样子，不是刚才那一份。
- 搜索被截断时（找到太多），只替换面板上列出来的那些文件——面板里没有的，编辑器不知道该改哪里。
- 单元测试：找出来的位置就是那段文字自己的位置（大小写不算时也是）、折叠后长度不一样的文字没有位置、面板有替换栏、`Tab` 轮转、替换栏里敲的字不进查找栏、没有找到就没有可替换的、跨文件替换（开着的进缓冲区、一次撤销回退、没开着的写进磁盘）；窗口级验收脚本证明：替换栏画出来了、没开着的那个文件在磁盘上真的换了。

**取舍**：替换是**按文件**做的——面板上找到的地方落在哪些文件里，就改哪些文件；同一个文件里的每一处都换掉。

### DF-0614 调试面板的调用栈（进行中：实现完成，窗口验收待跑）

调试面板原来只取**顶帧**：程序停在哪一帧是看得见的，但它是在哪一帧里停的、上面还有谁在调它，看不见；变量也只会是顶帧的那些。断点打在深层调用里的时候，顶帧往往不是那个人关心的那一帧。

验收标准：

- 程序停住时，**整条调用栈**摆在调试面板的左栏：从顶帧往下，一帧一行，每一行说清函数名、文件与行号（`helper() at main.rs:8`）。文件只写名字，不写从盘符起的长路径。
- **点哪一帧就切到哪一帧**：右边「变量」那一栏的标题变成那一帧的名字，变量换成那一帧的变量，挑中的那一帧在左栏有标记。切帧时旧帧的变量先清掉——留着就是撒谎。
- 切帧之后，**求值也在那一帧里问**（DF-0612 的表达式用的是当前挑中的帧号，不是顶帧）。
- 答案晚到不会串帧：适配器回的变量带着**它是哪一帧的**，回来的帧号不是屏幕上那一帧时，编辑器把它丢掉，不往面板上放。
- 一帧可能有好几组变量（局部变量、参数、全局变量）：**都显示**，不只显示最后回来的那一组。
- 面板**只看得下一屏**：栈比一屏深时显示前几帧，多出来的明说「…还有 N 帧」；变量多的时候同理（明说「…还有 N 个变量」），不悄悄截断。
- 没有变量时**明说**「没有变量」，不画一块空白。
- 单元测试：帧的一行文字（Windows 路径与 POSIX 路径、带行号与不带行号）、挑帧拿到帧号与名字、指针落在哪一行就挑哪一帧、指针不在那一栏或不在面板里就什么也不挑、只有屏幕上那一帧的答案才用；窗口级验收脚本证明：调用栈画出来了、挑中的那一帧有标记、**点第二帧之后标记挪到了第二帧上**。

**取舍**：假适配器给的栈是**三帧**（`main` / `helper` / `outer`），而且**每一帧的变量不一样**（第 1 帧是 `count`，第 2 帧是 `total`）——这样契约能验「编辑器问的是被挑的那一帧、拿到的是那一帧的变量」，而不只是「栈里有几行字」。真的适配器给多深的栈就是多深，编辑器最多显示一屏。

### 6.3 环境约束（影响验收怎么跑）

工作区目录 `D:\github\DocuFlowAI` 带 **Low 完整性标签**，因此在仓库里构建出来的程序（编辑器、测试二进制）都以低完整性运行，而**低完整性进程不能启动中等完整性的程序**。因此窗口级验收脚本把要运行的编辑器复制到工作区之外（`%LOCALAPPDATA%\CodeWeaver\check`）再运行。

语言服务器还有一处环境事实：本机的 `rust-analyzer` 是 rustup 的代理，而 `rust-analyzer` 组件**没有装在默认工具链里**，代理直接报「Unknown binary」。真正可用的二进制在 1.98.1 工具链下（`%USERPROFILE%\.rustup\toolchains\1.98.1-x86_64-pc-windows-msvc\bin\rust-analyzer.exe`），`rustfmt` 与它在一起。编辑器本来就有 `--lsp <program>`，验收脚本用它点名这个二进制——这是环境绕行，不是产品逻辑的改动。

另外，验收用的工程必须有自己的 workspace：`cargo locate-project` 会在工程落在别的 workspace 里时报「believes it's in a workspace when it's not」，因此工程放在工作区之外，并带一张空的 `[workspace]` 表。

**Git 也受同一条约束管**：`git.exe` 装在 `D:\Program Files\Git\cmd`，是中等完整性，而工作区里构建出来的二进制（包括 `cargo test` 的测试二进制）是低完整性，低完整性进程**起不了**它（`CreateProcess` 报 os error 5）。因此：

- 单元测试里的 git 检查**在 `cargo test` 里不会真的跑**：它们先试一次 `git --version`，起不来就把这一组检查整组跳过，并打印一行 `BLOCKED:` 说明为什么没跑。跳过不是通过——所以真正的证据由 `tools\git-unit-check.ps1` 给：它把测试二进制复制到 `%LOCALAPPDATA%\CodeWeaver\check` 再跑，那里是普通完整性，git 跑得起来。
- 窗口级脚本里的编辑器本来就是复制到工作区之外再跑的，所以改动面板里的 git 跑得起来；脚本用的仓库也放在工作区之外。

## 7. 本期结转

- 任务运行器现在能跑**构建任务**（`Ctrl+Shift+B`，命令由工程的清单决定）和**任意命令**（`Ctrl+Shift+P`，命令自己写，跑过的命令记在历史里，上下键就能翻出来）。还没做的是：命令的工作目录不能自己选（现在固定是打开的文件所属的工程目录）、历史不落盘（关掉窗口就没了）。任务运行器的进程模型已经定了（另起子进程、输出走管道、编辑器退出时任务被停掉），这几件是往上加东西。
- 交互式终端（DF-0610）现在是最小的一套：`Ctrl+Shift+T` 开一个长住的 shell，键盘焦点在终端上，回车把行写进 shell 的标准输入，`Esc` 把键盘还给编辑器而 shell 继续跑。它是**管道**不是伪终端（PTY），所以全屏程序（`vim`、`top`）在里面不工作，shell 的提示符也不回显（编辑器自己回显那一行）。还没做的是：Windows 上接 ConPTY 要真终端、终端的多标签与分割、工作目录能自己选、历史落盘、命令补全。终端和构建任务共用一个面板位置：终端开着时 `Ctrl+Shift+B` 起不来，状态栏会说明为什么。
- Git（DF-0602）已经定下用**命令行 `git`**（机器上有 git 就够，不引第三方库），代价是低完整性进程起不了 `git`（见 §6.3）。还没做的是：暂存区里挑文件（现在只暂存选中那一个）、取消暂存（`git restore --staged`）、在面板里看某一次提交（`git log`）、分支与远端（`git branch`、fetch/push）。
- 调试（DF-0606）现在只做到**最小**的一套：断点、单步、变量。还没做的是：命中次数、多线程、`debug console`、以及按工程配适配器（现在适配器在命令行上用 `--dap <program>` 点名，没有 `launch.json`）。断点按**位置**记着了（DF-0609）：文件改了行数之后断点会跟着它指着的那段文字走，适配器也会拿到新的行号。断点还能带**条件**了（DF-0611）：`Ctrl+F9` 写个条件，条件跟着断点走，也真的送到适配器；编辑器不检查条件写得对不对（那是适配器那边的语言），仓库里的假适配器也不求值条件。表达式也能问了（DF-0612）：`Ctrl+Shift+E` 写一个表达式，程序停住的时候问适配器，答案回到调试面板里。调用栈也看得见了（DF-0614）：面板左栏是整条栈，点哪一帧就切到哪一帧，变量与求值都跟着那一帧走；还没做的是：栈太深时的滚动、多线程（现在只跟踪一个线程）、以及从某一帧**直接跳到源码**（点栈里那一帧把光标送到对应的行）。表达式也还没做 watch（值变了就更新）与调试控制台（能一直开着往里写）。
- 格式化现在只接了 `textDocument/formatting`；按范围格式化（只排一段）与 `onType` 格式化留到后面。
- 重命名与代码操作共用一条「服务器改文件」的管道：一次事务落进缓冲区，没开着的文件写到磁盘。**写到磁盘的那部分撤销不回来**——这是与 VS Code 一样的取舍，但要说清楚。
- 还没接 `textDocument/prepareRename`（先问服务器这个名字能不能改）、没接重命名时的 `prepareCallHierarchy` 之类；代码操作没把诊断当上下文传给服务器（`context.diagnostics` 目前是空的）。
- `Ctrl+.` 已经用来取消 Agent 的一轮对话，所以代码操作用的是 `Alt+Enter`。
- 全局搜索（DF-0608）现在是最小的一套：在工程的文件里找字，列出找到的地方，挑一个打开那个文件并把光标放到那一行。还没做的是：正则与过滤规则（按文件类型、按路径排除）、大小写开关与全字匹配开关、多文件的批量替换（搜到的地方一起改）、搜索历史落盘。搜索是每次把工程走一遍（大工程要等），没有索引；找到的地方超过一千处时只留前面这些，面板会说明。
- 跨文件替换（DF-0613）把「搜到的地方一起改」做出来了：`Ctrl+Shift+H` 多一栏「替换」，回车就把面板上列出的那些文件里的每一处都换掉。还没做的是：只换其中一处（逐处替换）、按文件类型或路径过滤之后再换、以及替换前的预览（先看看会改成什么样，再决定改不改）。替换是按文件做的——面板上落在哪些文件里就改哪些文件；搜索被截断时只改面板上有的那些。
