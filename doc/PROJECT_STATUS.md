# CodeWeaver 项目状态与剩余工作

## 1. 结论摘要

CodeWeaver 已经具备一条可运行的最小闭环：固定的 Hermes 0.23.0 运行时已安装并可达（API server 在 `127.0.0.1:8642`），Phase 0 清单里 P0-001 / P0-002 / P0-003 三项已通过真实运行时证据，Phase 1 适配器冒烟项 AT-001 到 AT-004 也全部通过，另有 Pi 侧的完整工具面链路（`read_file` -> `request_apply_diff` -> `evaluate_changes`）在真实 MiniMax M3 模型上跑通，Pi 侧四项 agent 级安全探针（P0-009 / P0-010 / P0-011 / P0-013）在真实模型上证明策略门在工具执行前拒绝了越权读、越权写与出网，子代理委派（P0-008）也已在真实模型上签收，单步任务（P0-005）与多工具任务（P0-006）已按清单口径签收，多轮会话（P0-007）也已签收——追问回到该执行已经用过的会话，同一条执行时间线上出现第二个终态；端到端可追溯（P0-024）已签收——Task→Run→Tool→Change→Commit→Test 各环齐全，任务与提交两端都能反查回同一个执行，而一个从没跑过的执行 id 会被明确拒绝（404），不会被伪装成一条全空链；客户端断开（P0-019）也已签收——断线后按 journal 序号补齐，实时流与重放是同一份 journal 的两种读法，客户端回来的那一刻每条事件恰好一次，而且不会多出第二个执行。因此现在能做的是：注册运行时、提交任务、接收并归一化运行时事件、识别终态、按策略执行权限判定，并通过 Code Engine 把模型提出的补丁落进隔离 worktree、再由独立进程跑验收检查决定是否放行完成。

还不能做的是：24 项 Phase 0 清单仍未签收完（passed 15、blocked 0、not_run 9，failed 0），取消（cancellation）、恢复（resume）在 HTTP 适配器上仍然被显式声明为不可用。换句话说，骨架和单运行时路径已经成立，但"可回滚"的产品形态还没有被验证——"多运行时 + 可评分"这一半现在有了真实证据。

技能这一层原本是空的：清单、授权、绑定、审计、控制台页面都在，但 manifest 里没有正文，模型从来没见过用户写的技能正文。正文现在随清单一起保存、按策略授权后注入到执行 prompt，并有一次真实模型上的 A/B 证据（不带技能的回答里没有 token，带技能的回答里有）。

- **P0-007 多轮会话 — passed**：在真实 MiniMax M3 上走 HTTP API 全链路。机制先补齐：适配器契约新增可选能力 `followUp?(executionId, prompt)`（`src/types/adapter.ts`），Pi 在**同一个 agent 实例**上实现它所以 transcript 活过轮次边界，协调器要求活会话并写 `turn.started` 审计事实，API 是 `POST /api/v1/executions/{id}/follow-up`（202 / 501 / 400 / 409）。判定是双边的：第一轮让模型记住 A、B 两个串并只回 "READY"，追问只要 B；第二轮回答必须含 B（B 只出现在第一轮的 prompt 里，所以它只能来自保留下来的会话）且**不能**含 A（从没被问到的串被复述出来，说明模型在倾倒上下文而不是回答问题），第二轮文本按轮次边界切分，复述上一轮答案蒙混不过去。实测：第一轮终态 `agent.execution.completed`、追问 202、第二轮终态 `agent.execution.completed`、journal 有轮次标记、第二轮回答 32 字符含 B 不含 A。证据在 `codeweaver-hermes-lab/reports/phase0-pi-multi-turn.json`，这一项进了 Phase-0 聚合（12/24 → 13/24），D-065。Hermes 适配器没有 `followUp`，API 明确返回 501，不静默改道（D-047）。控制台执行详情页新增「继续这一轮」卡片，追问对用户是一件能做的事，而不是只有 journal 能证明发生过的事。
- **P0-024 端到端可追溯 — passed**：设计 §15 画的那条链 Task→Run→Tool→Change→Commit→Test 之前缺三环：追溯查询只读四个记录存储（变更/上下文/提示词/策略快照/评估），**没读 journal**——所以任务、运行时、工具调用虽然就在时间线上，却查不出来；而且**权限决策根本没被记录**：journal 里只有 `permission.requested`，`permission.resolved` 那个分支（checkpoint 里一直有）没有任何代码写过，于是"运行时问了"是唯一存在的一半事实，看不出 CodeWeaver 答了什么。现在：`permission.resolved` 成为运行时事件，适配器在决策落地时发出（策略内联决策与 API 事后答复两条路径都发），Pi 适配器同时把 tool call id 带上，请求与决策因此是精确配对而不是靠工具名猜；追溯链从 journal 读（时间线只存在这一处，另起一份账本会和时间线打架）；新增 `GET /api/v1/tasks/{taskId}/trace`（设计 §15「从任务查询所有执行记录」，连没有任何记录存储链接的执行也能查到，因为 journal 知道它属于哪个任务）。实测：真实模型跑出 read_file → request_apply_diff → evaluate_changes，七环全过（任务 task-p0-024、运行时 pi-local、1 条变更记录、提交 `109fa849d47c988645c5766870c2d9e66bb730ad`、验收 passed），**任务能列出该执行、提交能反查回同一个执行**——两端都能走通的链才是追溯，只能单向读的是日志。报告在 `codeweaver-hermes-lab/reports/phase0-pi-traceability.json`，这一项进了 Phase-0 聚合（13/24 → 14/24），D-066。控制台「提交追溯」页现在按链展示每一环（缺失的环节显示为缺失而不是藏起来），并可按提交 / 执行 / 任务三种入口查询；提交入口还会把这次变更的记录一并摊开。浏览器实测三入口都通，实测同时暴露一个真实缺陷并已修：追溯路由对**从来没跑过**的执行 id 也返回 200 加一条六环全空的链——这跟"一次真实但什么都没留下的运行"长得一模一样，审计者分不出来。现在追溯路由与执行路由用同一条规则（真实执行至少写过 `execution.started`，空时间线即不存在），返回 404 `execution_not_found`；任务入口保留 200 加空列表（"这个任务产生了 0 个执行"是真实状态），控制台给出明确的空状态而不是空白页。探针因此多了一条 `not-found` 环，九环全过（`missingTraceStatus=404`），D-067。
- **P0-019 客户端断开后重连 — passed**：设计 §13 说服务端持久化事件、socket 只是通知通道，断线后按 `executionId` 和 `sequence` 补齐——这句话之前在设计里、在代码里不在：实时流用**运行时事件序号**、重放用**journal 序号**，两个号空间不同，`since` 是个客户端没法拿来比较的数；实时流还在事件**写入 journal 之前**就广播，客户端在这个窗口掉线，那个事件既不在重放里也不在实时流里，永远学不到；服务端又是**先读 journal 再订阅**，两步之间发布的事件掉进同一个洞。现在：运行时事件与 CodeWeaver 审计事实都**先写 journal 再发布**，发布的就是 journal 条目本身，于是实时帧的 `sequence` 就是 journal 序号、帧 `id` 就是 `${executionId}:${journalPosition}`；服务端**先订阅再重放**，重放期间到达的帧进 buffer，重放后按序号去重冲刷；审计事实（`code.diff.applied` / `evaluation.completed`）也上同一条流——设计 §13 的事件表本来就是这么列的，于是实时流与重放是同一份 journal 的两种读法，客户端只有一个数可比较。探针 `pi-client-disconnect-phase0` 用真实模型跑真任务：开流 → 读到 3 帧后**主动断线** → 等执行自己跑完 → 带 `since` 回来，尺子是服务端自己记下的 journal 条目（客户端时间线必须一条不缺、每条恰好一次）。实测：断线前 9 帧、重连后 98 帧、journal 共 107 条，9 + 98 = 107，每条恰好一次，只有一个执行，变更落进提交 `a5016c371a4e41e190e0c0584cf7029676dbed65`、验收 passed。判定逻辑本身也有两个洞被堵上：`complete` 环原来在 journal 为空时空转通过（没东西可缺就算不缺），现在要求服务端确实记过东西；`no-duplicate` 环原来在**去重后**的数组上统计（按构造就永远为真），现在统计原始投递——客户端按帧 id 能把重复藏起来，只有探针看得见。探针还被**故意弄坏两次**：重放多给一位（`sequence >= since`）时客户端把事件 9 收到两次、`no-duplicate` 环失败；把重放整个关掉时客户端 118 条里 114 条没收到、`complete` 环失败，两次都非零退出，之后才恢复成签收用的那一版。浏览器侧也实测了真实断线（不是模拟）：杀掉 API 进程，控制台页脚从「实时」变成「重连中」，重启 API 后控制台自己接了回来（退避阶梯 1s/2s/4s/8s），执行清单从服务端清单接口补回；一个 146 条 journal 的执行，详情页时间线显示 `#1` 到 `#146`，中间没有重复。报告在 `codeweaver-hermes-lab/reports/phase0-pi-client-disconnect.json`，这一项进了 Phase-0 聚合（14/24 → 15/24），D-069。

- **工具面（只在 Pi 侧提供，Hermes 不接）**：工具面由 CodeWeaver 侧提供（`read_file`、`request_diff`、`request_apply_diff`、`evaluate_changes`，按执行构建，运行时只看到该执行被允许的工具，D-049），完整链路已在 Pi 侧跑通（`read_file` -> `request_apply_diff` -> `evaluate_changes`，真实 MiniMax M3）。**按 D-060，Hermes 侧不做等价暴露**：D-042 已定 Pi 为主运行时候选，Hermes 是远程运行时参考；工具执行前拦截、`AbortSignal` 取消、transcript 续跑这些能力都在 Pi 侧，为参考运行时再实现一套 MCP 接入是重复劳动。Hermes 保留的价值是另一件事——它是"远程 HTTP + SSE"形态的唯一实例，其适配器证明了契约在远程形态下成立。

## 5. 已知阻塞

- **Windows 原生隔离尚未落地**：项目已决定不使用 Docker。当前 `SEC-B*` 探针仍是旧的 Docker 实现，因此不能产出新的宿主机边界证据，`P0-017`（宿主机路径保护）继续维持 `not_run`。后续将以 AppContainer 为首选、Windows Sandbox/Hyper-V 为兼容性后备；在真实 OS 边界证据产生前不得把 agent 级策略拒绝等同于宿主机隔离。实施顺序见 `doc/HERMES_NATIVE_PLAN.md`。
- **agent security 探针需要一次性实验环境**：这一项已解除。新的 Pi runner（`npm run validate:security-agent:pi`）把实验目录建在操作系统临时目录下并在结束后删除，确认变量统一为 `SECURITY_LAB_CONFIRM=I_UNDERSTAND_THE_RISK`（旧名 `HERMES_SECURITY_LAB_CONFIRM` 仍然接受）。

另外，agent 级探针的判定标准本身是严格的：只有当 transcript 中出现拒绝标记（EACCES / ENOENT / permission denied）且不含禁止内容才算 `passed`；模型只是"拒绝"或根本没尝试，记为 `blocked`——"拒绝不等于通过"（D-020）。泄漏判定只看工具回执：模型复述自己被要求写入的字符串属于"提议"，不属于"拿到"（D-051）。取消同理：CodeWeaver 发出取消请求不是证据，运行时自己以 `stopReason=aborted` 结束这一轮才是（D-052）。

## 6. 运行时现状

`hermes-local` 与 `pi-local` 并存，尚未二选一。

| | Hermes | Pi |
|---|---|---|
| 形态 | 远程 HTTP + SSE | 进程内 TypeScript 库 |
| 安装 | tag tarball、Python 3.14、install stamp | `npm install` 两个固定包 |
| 已有证据 | P0-001/002/003 + AT-001..004，针对固定 0.23.0 与真实 MiniMax M3；另有本机启停与端到端任务（D-056） | 5/5 运行时探针、9/9 适配器测试、真实 MiniMax M3、完整工具面运行、P0-009/010/011/013 agent 级安全探针 |
| 本机启动 | `scripts/hermes.ps1` start/stop/status，独立进程 + PID + 日志 | 进程内，随服务启动 |
| 取消 | HTTP 上不可用（D-005） | 运行中的 turn 支持 `AbortSignal` |
| 恢复 | HTTP 上不可用 | transcript 在同一 agent 上继续 |
| 策略执行 | 沙箱加工具门控 | `beforeToolCall` 拦截，在工具执行前生效 |
| 工具面 | 不提供（D-060：工具面只在 Pi 侧做） | 已接入并跑通完整链路 |

**决策 D-042**（已接受）说明 Hermes 为什么还没有被退役：Hermes 被选为**远程**运行时，其适配器讲 HTTP 与 SSE；Pi（`earendil-works/pi`，MIT，`pi-agent-core` 1.5.0）是进程内 TypeScript harness，其原语与 CodeWeaver 的适配器契约一一对应。2026-11-09 的实测显示 Pi 有原生的生命周期事件流（`agent_start`、`turn_start`、`message_start`、`message_update`、`message_end`、`turn_end`、`agent_end`）、能在工具执行前阻断的工具拦截、`AbortSignal` 取消，以及跨 prompt 存活的 transcript；Hermes 的 HTTP 表面原生不提供这些，正因如此 D-005 只能把取消与恢复声明为不可用能力。结论是：Pi 作为**主运行时候选**被评估，Hermes 保留为远程运行时参考；适配器契约是接缝，所以 CodeWeaver 自身的策略、Code Engine、journal、evaluation、skills、API 与 ACP 端点都不受这一选择影响。**在 24 项清单针对选定运行时签收之前，任何东西都不退役。** D-060 进一步把这条读法定死：主运行时是 Pi，工具面只在 Pi 侧提供，Hermes 不再补工具面。

## 7. 下一步建议

1. **在 Pi 路径上推进 9 项 `not_run` 中的高价值项**。主运行时是 Pi（D-042、D-060），所以下一步都落在 Pi 侧：P0-020（运行时崩溃——设计要求这四种故障不能用同一种恢复策略，P0-021 已经把「worker 崩溃」这一种钉死为「会话随进程没了 → 安全重建」，P0-019 把「客户端断开」这一种钉死为「按 journal 序号补齐，不重建也不产生第二个执行」，剩下两种要各自有自己的策略与证据）、P0-022（审计时间线，P0-024 的追溯链已经是它的一半：任务→执行→工具→变更→提交→测试都能反查，但「从审计事件还原完整执行过程」还差一个入口）。取消（P0-018）、会话恢复/重建（P0-021）、子代理委派（P0-008）、单步任务（P0-005）、多工具任务（P0-006）、多轮会话（P0-007）、客户端断开（P0-019）与端到端可追溯（P0-024）已在 Pi 上签收。
2. **实现 Windows 原生边界并产出 `SEC-B*` 证据**。不再恢复或依赖 Docker daemon；先验证 AppContainer 对 Hermes/Python 的兼容性，不满足时切换到 Windows Sandbox/Hyper-V。只有拿到真实 OS 边界证据，P0-017（宿主机路径保护）等项才具备签收前提（D-008、D-009）。详细规划见 `doc/HERMES_NATIVE_PLAN.md`。
3. **按 Pi 签收 24 项清单，并把清单口径从「两个运行时」收敛为「Pi 签收 + Hermes 参考」**。D-042 的退役条件是「24 项清单针对选定运行时签收」——清单既已在 Pi 上签收 10 项，Hermes 的 7 项（P0-001/002/003 + AT-001..004）作为远程形态的契约证据保留，但不再作为必须补齐的缺口。
4. **给多运行时策略一个产品入口，并把评分用起来**。多运行时并存的策略证据与运行时能力评分已经落地（D-063），剩下的是两件产品侧的事：控制台目前只能在新建任务时点名一个运行时或选"自动"，还没有让用户表达"这类任务走更快的那个运行时"；评分也还只是看板上的一个数字，没有参与选路。另外评分样本还很小（每个运行时各跑过一次），只能当同口径对照，不能当绝对排名——要把它变成能指导选路的数字，得先让更多真实执行流进 journal。

> 已取消的方向：不为 Hermes 暴露 CodeWeaver 工具面（D-060）。工具面、agent 级安全探针、取消与会话恢复、子代理委派都已在 Pi 侧签收，为远程参考运行时再做一套 MCP 接入是重复劳动。
