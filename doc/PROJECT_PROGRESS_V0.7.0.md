## 1. 本期结论

V0.6.0 把编辑器从「能读能高亮能补全能跑 Agent」推到了「像个开发工具」：语言服务器、调试适配器、Git、终端、任务、全局搜索、跨文件替换都在了。收口那轮（2026-11-25）又挖出六个真缺陷并修掉，自动化测试 538 项全绿——细节见 [V0.6.0 §6.2](./PROJECT_PROGRESS_V0.6.0.md)。

这一期做**外壳与命令系统**：把编辑器从「一堆功能各自占一个键」变成「像 VS Code 那样的编辑器」。

差距不在功能清单，在三根骨头：

1. **没有统一的命令系统**：现在每个功能都是一条硬编码的按键分支（二十来条），键位写死在代码里，面板提示、状态栏、帮助各写一份。想加一个功能就得改三处。
2. **没有命令面板**：`Ctrl+Shift+P` 现在是「运行一条命令」输入框，跟 VS Code 的「列出所有命令」正好相反——这是最刺眼的不一致。
3. **没有活动栏**：左边只有一个文件树，没有 VS Code 那条竖着的活动栏，侧边栏也没法分区切换。

本期做四件事：

1. **DF-0701 命令注册表**（新组件）：命令有 id、标题、键位、什么时候能用、怎么执行；键位写成 `ctrl+shift+p` 这样的字符串，能解析、能查冲突。
2. **DF-0702 命令面板**：`Ctrl+Shift+P` 列出所有能用的命令，输入字过滤，上下键挑，回车执行；面板上写着每个命令的键位。
3. **DF-0703 活动栏与侧边栏分区**：左边一条活动栏（资源管理器 / 搜索 / 源代码管理 / 调试 / 扩展），点哪个侧边栏就显示哪个分区；文件树成为「资源管理器」。
4. **DF-0704 键位可改**：键位从注册表来，可以改（`keybindings.json`），改完立刻生效；设置面板里能看到。

先立 DF-0701 与 DF-0702：命令注册表是**所有**后续工作的地基（活动栏的菜单、键位设置、状态栏提示都从它取），面板则是人一眼能看见的成果——按一下 `Ctrl+Shift+P`，编辑器所有的功能列在那里。

## 3. V0.7.0 开发项

### DF-0701 命令注册表（进行中）

命令是编辑器里「能做的事」的一条登记：它有名字（给人看）、有 id（给代码看）、有键位（给人按）、有条件（什么时候能用）、有做法（怎么执行）。

现在这些散在二十来条按键分支里。这一项把它们收进**一个组件**（`platform` crate 里的 `commands` 模块），按键路由不再认识每个功能，只问注册表：「这个键是谁的？」

验收标准：

- **每条命令有五个字段**：`id`（小写点分，如 `editor.format`）、`title`（给人看的中文，如「格式化文档」）、`keybinding`（如 `ctrl+shift+f`）、`when`（什么时候能用）、`run`（怎么执行）。
- **键位写成字符串**：`ctrl+shift+p`、`alt+shift+f`、`f9` 这样写；解析器认得 `ctrl`/`alt`/`shift`/`cmd` 四个修饰键与一个主键（字母、数字或具名键）。解析不出来的时候**明说**（返回错误并说明是哪个键位），不猜。
- **注册表能查冲突**：两个命令抢同一个键时，注册表**说得出**是哪两个命令、哪个键——不静默地让一个盖掉另一个。
- **命令能列出**：注册表按 id 排序列出所有命令，面板与设置面板都从它取，不各写一份。
- **命令能按条件问「现在能不能用」**：比如「重命名」要光标处有个名字、「调试」要先有调试会话——条件不满足时命令**仍然列出来但是灰的**，跟 VS Code 一个样。
- **注册表是纯数据 + 纯函数**：它不认识 `NativeApplication`，只负责「谁、什么键、能不能用」；执行由调用方给。这样它能被单元测试钉住，不用开窗口。
- 单元测试覆盖：键位解析（各种写法 + 认不出来的写法）、冲突检测、条件判断、按 id 排序、id 重复时报错。

### DF-0702 命令面板（进行中）

`Ctrl+Shift+P` 打开一个面板，列出编辑器所有的命令——跟 VS Code 一个路子。

验收标准：

- **`Ctrl+Shift+P` 打开命令面板**（不是现在的「运行命令」输入框了）：面板盖住窗口，上头是输入框，下头是命令列表。
- **面板列出所有能用的命令**：每行写着命令的标题和它的键位；命令太多时按标题过滤（输入几个字，列表跟着变），过滤是**大小写不算**的（跟搜索面板一个规矩）。
- **上下键挑、回车执行**：`Esc` 关掉面板；没挑之前什么都不改。
- **挑一个命令就等于按了它的键**：命令面板走的是同一套「命令 → 执行」，所以从面板里跑出来的效果，跟直接按快捷键一样。
- **不能用的命令灰着**：条件不满足的命令列出来但是灰的，挑它的时候编辑器**明说**为什么不能跑，不静默什么都不发生。
- **命令面板能调到「运行命令」**：原来那个 `Ctrl+Shift+P` 的输入框（跑一条任意命令）挪到 `Ctrl+Shift+U`，并且在命令面板里也有一条「运行命令…」。
- 输入框开着的时候它自己吃键：命令不会被敲进正文里。
- 单元测试覆盖：面板打开/关闭、过滤、上下键、回车执行、灰命令不能跑；窗口级验收脚本证明：按 `Ctrl+Shift+P` 面板真的开了、命令列出来了、挑一个之后它真的执行了。

### DF-0703 活动栏与侧边栏分区（计划）

左边一条竖着的活动栏，点哪个分区，侧边栏就显示哪个。

验收标准：

- 活动栏在窗口最左边，竖着排五个图标：**资源管理器**（文件树）、**搜索**、**源代码管理**（Git）、**调试**、**扩展**（占位，扩展生态不在本期）。
- 活动栏占住一条竖的窄条，文件树挪到活动栏右边；窗口的正文区域相应窄一点。
- 点哪个图标，侧边栏就显示哪个分区；再点同一个图标收起侧边栏（跟 VS Code 一样）。
- 分区切换是**状态**：切走了再切回来，内容还在。
- 每个图标旁画一个**徽标**：Git 分区旁边画改过的文件数、调试分区旁边画断点数——跟 VS Code 一个样。
- 键盘也能用（上下键在活动栏上换分区），不强迫人用鼠标。
- 单元测试覆盖：分区状态、徽标的数字、收起/展开；窗口级验收脚本证明：活动栏画出来了、点第二个图标侧边栏换了、徽标的数字对。

### DF-0704 键位可改（计划）

键位从注册表来，所以它就能改。

验收标准：

- 键位存在一个文件里（`keybindings.json`，放在工程根或者用户目录），格式是 `[{ "key": "ctrl+shift+p", "command": "editor.format" }]`。
- 改了这个文件，编辑器**下次启动**就用新的键位；键位写错（命令不存在、键位写不成）时编辑器**明说**哪一条不对，不静默忽略。
- 设置面板里能看见每个命令现在的键位，也能改常用的几个（不写文件也能改，改完立刻生效，关掉窗口就没了——跟其它设置项一个待遇）。
- 命令面板里每一行都写着命令现在的键位。
- 单元测试覆盖：键位文件的解析、写错时的说法、覆盖之后注册表查出来的键位变了。

## 5. 开发规则

1. 每个版本先更新对应版本文档，再实现文档内编号任务。
2. 产品版本必须与主进度文档号相同；跨子项目不得出现不同产品版本。
3. “完成”必须同时具备实现、自动化测试和可追溯验收结果。
4. Mock 契约通过与真实运行时通过分别记录，不互相替代。
5. 未完成项只能标记为计划、进行中或阻塞，不以界面占位视为完成。
6. **开发优先，测试收口**：实现过程中不跑全量回归，也不跑窗口级脚本（它们会抢焦点、打断人）；回归集中到一轮里跑完，验收数字回填进 §6.2。

以上规则的完整版（含常用命令、代码风格、Windows 环境约束与 Git 约定）见仓库根的 [AGENTS.md](../AGENTS.md)。
