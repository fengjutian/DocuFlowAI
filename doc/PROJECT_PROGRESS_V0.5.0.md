# CodeWeaver 项目进度与开发计划 V0.5.0

文档号：`V0.5.0`  
产品版本：`0.5.0`  
状态：已实现并验收（结果见 §7.2）  
更新日期：2026-11-12

## 1. 本期结论

V0.4.0 把编辑器变成了一个「工作区」：文件树、多标签、脏状态、外部变更冲突、后台解析与大文件降级都到位了。但编辑器与 Agent 之间仍然只有一根线——把当前文本整段丢过去，收一串文字回来。

这一期把那条线补成闭环：**用户挑上下文 → Agent 提改动 → 编辑器按文件/按块批准或拒绝 → 批准的部分写进缓冲区 → 每一环都可追溯**。

本期做五件事：

1. **上下文选择器**：Agent 面板里能挑要送出去的上下文（当前文件、选区、其它打开的标签），默认只送用户选中的；密钥类文件默认不送。
2. **Diff 预览与按块批准**：Agent 的改动以变更块（hunk）呈现，逐块批准或拒绝、整文件批准或拒绝；批准的部分作为一次可撤销事务写进缓冲区。
3. **基于 BufferVersion 的冲突检测与三方合并提示**：提案进来时记下缓冲区版本；应用时若版本已经变了，不静默套用旧补丁，改用 diff3 三方合并，冲突交给用户选。
4. **可追溯**：执行、变更、检查、审批、应用结果都在编辑器内留痕，能翻回去看当时发生了什么。
5. **设置面板的第一项**：降级阈值此前只能从命令行给，本期搬进编辑器内的设置面板（`Ctrl+,`），改值即时生效。

## 3. V0.5.0 开发项

### DF-0501 Agent 面板接入上下文选择器（已完成）

验收标准：

- Agent 面板列出可用的上下文来源：当前文件、当前选区、其它打开的标签；每一项显示路径与大小，用户可逐项勾选。
- 默认只发送用户明确勾选的上下文；未勾选的项不进入请求体。
- 密钥类文件（`.env`、`credentials*`、`*.pem`、`*.key`、`id_rsa*`、`.npmrc`、`.pypirc`）默认不出现在可选项里，且即使被选中也不发送内容。
- 上下文以 ACP 的 `resource` 块发送（`{type:"resource", uri, text}`），端点把它渲染成带路径标题的文本段，模型能看见内容与来源。
- 提示词与上下文分开：提示词是用户写的话，上下文是附带的材料，二者在请求体里不是同一段文本。
- 上下文选择器的状态有单元测试；协议序列化与端点解析各有契约测试。

### DF-0502 Agent Diff 预览、按文件/按块批准与拒绝（已完成）

验收标准：

- Agent 提出的改动在编辑器里以**变更块（hunk）**呈现，一块一块列出新增行与删除行；不是一整段新文本。
- 批准与拒绝的粒度是块：能批准一块、拒绝一块；也能整文件批准、整文件拒绝。
- 被拒绝的块不进入应用结果；应用结果只由被批准的块决定。
- 批准的内容作为**一次**事务写进缓冲区（一次撤销即可整体回退），并把文件标记为已修改。
- 应用结果、批准数、拒绝数在面板上写明，不出现「不知道到底改了什么」的状态。
- 变更块的解析、按块应用、整文件批准/拒绝都有单元测试。

### DF-0503 基于 BufferVersion 的冲突检测和三方合并提示（已完成）

验收标准：

- 提案到达时记录当时的缓冲区版本；应用前若版本已经变了，不把旧补丁静默套到新文本上。
- 版本一致时干净应用；版本不一致时走三方合并：基线（Agent 看到的原文）、我方（当前缓冲区）、对方（提案应用后的文本）。
- 三方合并用 diff3 的区域规则：只有一方改动的区域取那一方，双方改成一样的取一次，双方改成不一样的算冲突。
- 有冲突时不写入，在面板上把冲突区域与两种候选摆出来，由用户逐个选择保留哪一边；用户不选就不写。
- 三方合并的算法有单元测试，覆盖「双方改不同处干净合并」「双方改同一处冲突」「相邻两行改动也算冲突」这几种情形。

### DF-0504 执行、变更、检查、审批和应用结果在编辑器内可追溯（已完成）

验收标准：

- 面板能翻看本次会话的轨迹：每一轮的执行、Agent 调过的工具、提出的变更、用户的每一次批准/拒绝、最终应用到缓冲区的结果，各有一条记录。
- 每条记录带类别与内容，能分清「Agent 做了什么」与「用户批准了什么」。
- 应用后的记录带上写入前后的缓冲区版本，能看出这次改动落在哪个版本上。
- 轨迹在会话进行中持续追加，不因新一轮开始而丢失上一轮。

### DF-0507 降级阈值的设置界面（已完成）

承接自 V0.4.0：阈值此前只能从命令行给（`--highlight-limit` / `--highlight-lines`），改一次要重启一次编辑器。本期把这两项搬进编辑器内的设置面板，作为通用设置面板的第一项。

验收标准：

- 编辑器内有设置面板，`Ctrl+,` 打开；面板打开时独占键盘：`Esc`/`Enter` 关闭，`↑`/`↓` 选设置，`←`/`→` 改值。
- 面板第一项是「高亮大小上限」，第二项是「高亮行数上限」；取值是**离散档位**而不是自由输入（大小：100 KB / 250 KB / 500 KB / 1 MB / 2 MB / 5 MB / 10 MB / 20 MB；行数：5,000 / 10,000 / 20,000 / 50,000 / 100,000 / 200,000），方向键就能改完，不依赖键盘布局。
- 面板的初值是当前生效的策略；命令行给的 `--highlight-limit` / `--highlight-lines` 仍然生效，作为面板的初值。
- 改值**即时生效**：当前文件与已经打开的其它文件一起换策略，状态栏的「降级模式」提示随之更新。
- 阈值放宽后，此前被降级（不做高亮）的文件恢复语法高亮，不被「已经问过高亮器」的缓存挡住。
- 面板模型（档位选取、上下移动、改值）与按键处理有单元测试；窗口级验收脚本证明面板能打开、能改值、改值后高亮真的回来。
- 本期设置**不持久化**：编辑器还没有应用数据目录的概念，重启后回到默认值；持久化等设置面板有第二项时一起做。

## 6. 本期协议约定

本期改了两处协议形状，编辑器与 Hermes Lab 端必须同步，否则契约测试会红。

### 6.1 提示词里的上下文块

`session/prompt` 的 `prompt` 数组现在接受两种块：

```json
{ "type": "text", "text": "把这段函数改成异步" }
{ "type": "resource", "uri": "src/app.rs", "text": "fn main() { ... }" }
```

端点把 `resource` 块渲染成带路径标题的文本段再交给模型，路径必须留在内容里——模型要知道这段文字是哪来的。

### 6.2 工具调用里的 diff 内容块

`session/update` 的 `tool_call` 携带 `kind` 与 `content`：

```json
{
  "sessionUpdate": "tool_call",
  "toolCallId": "call-1",
  "title": "request_diff",
  "kind": "edit",
  "status": "in_progress",
  "content": [
    { "type": "diff", "path": "src/app.rs", "patch": "@@ -1,3 +1,4 @@\n..." }
  ]
}
```

`patch` 是统一 diff 文本。编辑器按它切出变更块。本期先只支持这一种形状；ACP v1 的 `{type:"diff", path, oldText, newText}` 留待后续版本补上——补上时编辑器优先用 `oldText`/`newText`，因为那份基线更准，三方合并也更好做。

### 7.3 期间修掉的真缺陷

1. **Agent 的路径与编辑器的路径对不上**：Agent 给的是相对路径（`fixture.txt`），编辑器用的是绝对路径，两者是按字符串相等查的，于是改动永远落不到打开的文件上——批准与应用的按键全都空转。现在按「同一个文件」判定（尾段相同即算同一个），同名文件有歧义时不做任何事。
2. **窗口事件循环从不记录改动的基线**：Agent 的输出被收集了，但收集之后没有记录「提案到达时缓冲区是哪个版本」，冲突检测因此形同虚设；同时事件循环在无事发生时不会重绘，Agent 的答复要等用户碰一下鼠标才出现。
3. **应用改动后标签页没有标记为已修改**：状态栏有「●」，标签条上没有——标签的脏标记只在键盘输入与保存时刷新。
4. **中文输入法下带 Ctrl+Alt 的按键在窗口里没有名字**：winit 按当前输入法布局取逻辑键，中文布局没有 Ctrl+Alt 组合的映射，这些键以「无名键」到达，编辑器按字符匹配就永远匹配不上。现在按虚拟键码兜底，取的是与布局无关的字母与数字。
5. **设置面板画在文字下面**：渲染器先画所有矩形、再画所有文字，窗口里其余的文字因此压在面板的背景上，面板几乎读不了——正文和面板的字叠在一起。现在面板打开时窗口的其余部分根本不画：面板下面没有文字，而不是文字盖在面板上。
6. **提高阈值之后高亮回不来**：编辑器记得「已经问过高亮器」，记住的还是旧阈值下的那次提问，阈值放宽后就不再问一次，文件一直是灰的。现在换阈值时清掉这个记录，高亮器重新被问一遍。

### 7.4 环境约束（影响验收怎么跑）

工作区目录 `D:\github\DocuFlowAI` 带 **Low 完整性标签**，因此在仓库里构建出来的程序（编辑器、测试二进制）都以低完整性运行，而**低完整性进程不能启动中等完整性的程序**——ACP 端点（node.exe）会以「拒绝访问」被拒。两个后果：

- `cargo test` 里的 ACP 契约测试会**悄悄跳过端点**（测试结果仍显示「ok」），看上去像通过，其实什么都没验。
- 编辑器在仓库里构建出来的那份无法启动 Agent 端点，窗口级闭环无从跑起。

因此 `tools\acp-contract-check.ps1` 与 `tools\agent-check.ps1` 都把要运行的二进制复制到工作区之外（`%LOCALAPPDATA%\CodeWeaver\check`）再运行；契约脚本在端点不可用时**判失败**，不再让测试悄悄跳过。这是环境标签带来的绕行，不是产品逻辑的改动。

## 8. 本期结转

- 文件树的全局搜索与项目索引（DF-0505）需要一套后台索引与首批结果的延迟预算，编辑器还没有任何后台索引设施；设置面板本期已经成型（DF-0507），索引留给 V0.6.0 与设置面板的第二项一起做。
- 会话恢复（DF-0506）需要先定下「恢复什么」的边界（标签、滚动位置、选区、未保存内容），否则存下来的东西用户也不认；本期不存。
- 设置（DF-0507）本期只做降级阈值两项，且不持久化；等设置面板有第二项时，再一起定下设置文件的位置、格式与迁移。
- 运行时评分参与选路（DF-0508）在控制台侧，不在编辑器侧；本期编辑器不碰选路。
- 本期 Diff 提案只支持统一 diff 文本这一种形状；ACP v1 的 `oldText`/`newText` 形状、删除/重命名/新建文件的操作语义留到后续版本。
- 本期三方合并只处理文本行；语义冲突（两边各自改名、合并后编译不过）靠构建与测试发现，编辑器不假装能判断。
- 上下文选择器本期只覆盖当前文件、当前选区、其它打开的标签；诊断与 Git 状态作为上下文来源留到后续版本。
