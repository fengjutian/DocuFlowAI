# ADR-0005：UI 层独立成 crate，字体测量由渲染层注入

- 状态：已接受
- 日期：2026-11-11
- 适用范围：`editor/crates/ui`、`editor/crates/render`、`editor/crates/platform`、`editor/crates/text`

## 背景

ADR-0004 之后，编辑器已经能打开文件、编辑、保存，但窗口里那块"正文区域"其实
不是编辑器：**它把整个文档当成一段文本丢给渲染器**，用一个大矩形裁掉溢出部分。
后果是：

- 没有光标（连一个闪烁的竖线都没有），用户不知道自己在哪；
- 没有命中测试，鼠标点不到字符位置；
- 没有选区、没有滚动，文本超出视口就再也够不着；
- 文档一长就慢：每次重绘都要重新排版整篇文档，而屏幕上只看得见几十行。

这就是"带文本框的窗口"和"编辑器"的差别。阶段 1 要求把这一层补齐。

## 决策

### 1. 新建 `ui` crate：布局、命中测试、视图状态

`ui` crate 只依赖 `text` crate，装着三样东西：

- `measure`：**怎么量文字**的抽象（`TextMeasurer` trait）与一个不需要字体的
  `MonospaceMeasurer`（供测试与降级使用）；
- `layout`：**文字排在哪**——把缓冲区变成看得见的若干条*视觉行*
  （`VisualLine`），每行带着每个字节边界的 x 偏移；以及反向的命中测试
  （点 → 偏移、偏移 → 点）；
- `view`：**屏幕状态**——滚动位置、光标的矩形、选区在每条视觉行上的矩形。

`ui` **不依赖 `render`**。原因是依赖方向：`platform -> render` 与
`platform -> ui` 是两条独立的边，让 `ui` 依赖 `render` 会把「谁来排版」
和「谁来画」耦在一起。

### 2. 字体测量通过 trait 注入，由 platform 委托给渲染器

布局必须知道每个字符落在哪，否则光标会落在两个字符之间。真正知道这件事的只有
渲染器——它拥有字体系统与整形（shaping）。因此 `ui` 只声明需求：

```rust
pub trait TextMeasurer {
    fn measure(&mut self, text: &str, font_size: f32) -> LineMetrics;
}
```

`platform` 用 `Renderer::measure_text` 实现它（`RendererMeasurer`）。于是：

- 测量走的是与绘制**同一条**整形路径，光标落在字形上而不是字的旁边；
- `ui` 的测试不需要字体系统，也不需要 GPU；
- `render` 仍然不知道 `ui` 的存在。

### 3. 布局按视口构建，并且缓存

布局只测量**看得见**的行：为了画四十行去排版一百兆的文档是荒谬的。`TextLayout::build`
接受起始行号、能放下的行数与可用宽度，返回这些行的视觉行。

测量不是免费的，所以布局被缓存：只有**文本版本、视口尺寸、滚动位置**三者之一
变了才重建（`EditorView::built`）。鼠标移动因此不必重排文本。

### 4. 换行只做一次

换行由 `ui` 层完成：一条逻辑行按视口宽度切成若干视觉行，每条视觉行单独绘制。
渲染器**不得**再换一次——所以每个 glyph run 的绘制宽度给到视口宽度的两倍，
渲染器的换行阈值就不会被触发；真正裁剪靠 clip。

（早先的实现在渲染器里靠 `set_size` 换行，于是同一段文本被换行两次：一次在布局里
算视觉行，一次在渲染器里决定断在哪里。两套换行规则必然对不上。）

### 5. 交互接在 `platform` 的事件循环里

- **点击**：`hit_test` 得到字节偏移，`Editor::select_range` 把光标放过去；
- **拖拽**：按下时记住锚点，移动时把选区拉到当前偏移；
- **滚轮**：`ViewState::scroll_lines`，方向按 winit 的约定取反（正 delta = 滚向
  用户 → 往下滚），并夹在文档范围内；
- **上下键**：按**视觉行**移动，保持列位置；目标行不在视口内时先滚动再移动；
- **Home/End**：移到当前逻辑行的首尾；
- 任何会移动光标的操作之后都调用 `ensure_caret_visible`，光标离开视野时视图跟随。

### 6. IME 预编辑画在光标所在行

预编辑文本不属于缓冲区，它属于光标所在的那一条视觉行：把它接在光标前后两段
文字之间画（两段之间留出它自己的宽度），其余行照常。缓冲区里仍然只有已提交的
文本。

## 后果

- 窗口里的正文区域现在是真正的编辑器：等宽字体、逐行绘制、超宽自动折行、
  可见光标、鼠标点击定位、拖拽选区、滚轮滚动、键盘上下移动且保持列位置。
- 中文输入的预编辑（拼音）显示在光标处，不再把整篇文档重新排一遍。
- `ui` crate 有 18 个测试，全部不需要 GPU；`platform` 另有 19 个测试覆盖
  接线层（滚轮方向、光标移动、光标跟随）。
- 已知限制（留待后续）：
  - 滚动以**逻辑行**为单位；折行后"一屏"能装多少逻辑行并不固定；
  - `ensure_caret_visible` 用视觉行数估算可见逻辑行数，折行密集时是近似值；
  - 光标不闪烁；
  - 没有语法高亮；
  - 制表符按渲染器的默认宽度显示，没有实现"制表位"。

后续：[ADR-0006](0006-shape-cache-and-perf-baseline.md) 处理了这一层带来的性能问题
——同一段文字每帧被整形两次，打字一帧要 11.6ms；
[ADR-0007](0007-multiple-selections.md) 把选区从"一个"变成"一组"，多光标由此而来。
[ADR-0008](0008-find-and-replace.md) 在这组选区上加了查找替换。

## 被否决的方案

- **按字符宽度估算布局**（例如"每个字符 8 像素"）：不需要字体系统，但光标会
  落在字形的左边或右边，尤其是在比例字体和中文上。字形位置必须由整形决定。
- **让 `render` 负责换行，`ui` 只算行号**：看起来更省事，但渲染器的换行阈值与
  布局的换行规则是两次独立判断，边界一旦不一致，视觉行与实际绘制的行就会错位。
  换行必须只有一处。
- **一次性测量整个文档**：文本一长就爆内存，而且绝大多数行根本不会被画到。
- **把视图状态（滚动、光标矩形）放进 `editor-core`**：`editor-core` 只该知道
  文档与选区。滚动位置是展示状态，与文档无关。
- **让 `ui` 直接依赖 `cosmic-text`**：`ui` 会变成第二个排版实现，且失去"不测量
  也能用"的降级能力（`MonospaceMeasurer`）。
- **在 `ui` 里缓存每个字符的宽度表**：宽度依赖字体、字号与上下文（连字、组合
  字符），缓存表很快就会和实际绘制对不上。缓存的是**布局**，而不是宽度。
