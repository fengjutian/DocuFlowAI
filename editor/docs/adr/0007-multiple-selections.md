# ADR-0007：选区是列表，编辑一次应用全部光标

- 状态：已接受
- 日期：2026-11-12
- 适用范围：`editor/crates/editor-core`、`editor/crates/platform`、`editor/crates/ui`

## 背景

编辑器此前只有**一个**选区：一个 anchor 和一个 head。这带来两个限制：

- 查找替换要一次改很多处时，只能一个一个来；
- LSP 与 Agent 带来的"多处修改"没有落脚点——它们要的是一组编辑，
  而编辑器一次只接受一个。

这三件事（查找替换、LSP、多光标）共用同一个地基：**一组选区**。所以地基先改。

## 决策

### 1. 选区是列表，不是单个

`Editor` 持有 `Vec<Selection>`，而不是 `Option<Selection>`。

- 列表按**文本位置**排序，所以第一个就是最上面那个（primary）；
- 至少有一个：编辑永远有一个光标；
- 每个选区仍然是 anchor + head 一对锚点，编辑之后由 buffer 重新解算。

### 2. 一次编辑 = 一个事务里的多个编辑

`Editor::replace_ranges` 把所有选区的范围合并、排序，交给 `Transaction` 里的
`Vec<TextEdit>` 一次应用：

- `text` crate 的事务本来就支持多个编辑，而且要求**按起点排序、互不重叠**，
  从后往前应用；
- 范围重叠时（比如一个光标落在另一个光标的选区里）**合并**成一个——文本只有
  一个地方能放新文字，合并让编辑始终有定义；
- 合并之后每个光标的新位置可以**算**出来：排好序的范围里，前面的每一次改动
  都会把后面的往后推，所以新光标 = 范围起点 + 前面改动的净长度 + 插入长度。

一次多光标编辑在撤销历史里是**一步**（不是 N 步）：撤销一次全部回去。

### 3. 交互

| 操作 | 效果 |
|---|---|
| `Ctrl`+点击 | 加一个光标（不清掉已有的） |
| `Alt`+`↑`/`↓` | 在上/下一行加一个光标 |
| `Esc` | 只留 primary 光标 |
| `Shift`+方向键 / `Home` / `End` | 扩展选区（锚点不动，头移动） |
| 输入 / 退格 / `Delete` / 方向键 | 作用于**所有**光标 |

顶栏显示当前光标数（"光标 3"），这样多光标是看得见的。

### 4. 绘制

`EditorView::draw` 遍历所有选区画选区矩形、遍历所有选区画光标。`ui` crate 不需要
改：它已经只认"一个偏移对应一个矩形"，多光标是**调用方**循环的问题。

## 后果

- 多光标可用：Ctrl+点击加光标，输入时每个光标处都写进去。
- 查找替换与 LSP 的"多处编辑"现在有落脚点了：一次事务里多个编辑。
- 撤销历史里的一次编辑 = 一步；多光标编辑也是一步。
- 选区列表按文本位置排序，所以"primary"是最上面的那个——与 VS Code 不同
  （VS Code 的 primary 是最后交互的那个）。Esc 之后留下的是最上面的光标。
- 扩展选区时锚点不动、头移动，所以 `Shift`+方向键可以来回缩放选区。
- **winit 的修饰键读的是真实键盘状态**（`GetAsyncKeyState`），所以合成的
  `WM_KEYDOWN` 不会让 winit 以为按住了 Ctrl——自动化装置**无法**模拟 Ctrl+点击。
  多光标的绘制因此由单元测试覆盖（不需要 GPU），真窗口装置仍然验证单光标、
  选区和文本的渲染。

## 被否决的方案

- **在 `editor-core` 之外做多光标**（比如在 `platform` 里维护一份光标列表）：
  那样编辑（`Editor::insert`）看不到别的光标，一次输入只会写进一个地方。
- **每个光标各做一次事务**：撤销历史会变成 N 步，撤销一次只回退一个光标，
  用户会认为撤销坏了。
- **用"多次单次编辑"模拟多光标输入**：光标位置会在前面几次编辑后失效，
  必须手工重算偏移——正是 `replace_ranges` 里已经算好的那套。
- **重叠的选区直接拒绝**：用户点了另一个光标的选区里就会失去一个光标，
  体验比合并差。合并后两个光标落在同一处，行为是确定的。
- **把 anchor 和 head 用同一个锚点**（省一次分配）：释放 head 时会把 anchor
  一起废掉，选区会莫名其妙地回到文档开头。测试抓到了这个坑。
