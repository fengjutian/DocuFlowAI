# ADR-0010：语言服务器走 LSP，自建轻客户端，诊断与补全先落地

- 状态：已接受
- 日期：2026-11-12
- 适用范围：`editor/crates/lsp`、`editor/crates/platform`、`editor/crates/app`

## 背景

计划 §5.1 的 MVP 清单里有"语言服务器（LSP）"。这一条不是"接一个库"就完事的，
它要回答四个问题：

1. **谁来当客户端**：现成的 Rust LSP 客户端有 `lsp-server`、`lsp-types`、
   `tower-lsp` 等，但它们大多是为**服务端**写的，或者把编辑器绑死在某个框架上
   （`lsp-types` 只提供类型，消息收发还得自己写）。
2. **位置怎么算**：LSP 的位置是"行 + **UTF-16 code unit** 列"，编辑器算的是字节
   偏移。两套坐标混用是最容易出错的地方。
3. **改动怎么同步**：协议分"整篇同步"和"增量同步"，服务器在 `initialize` 的回答里
   声明自己要哪一种；客户端给错就会让服务器的文档内容错乱。
4. **先做哪些功能**：诊断、补全、跳转、引用、重命名、格式化……一次做完不现实，
   要挑出**用户看得见**的那几个。

## 决策

### 1. 独立的 `lsp` crate，自己写帧和分发

`editor/crates/lsp` 依赖 `codeweaver-text` + serde，**不依赖** `render`、
`editor-core`、`platform`。它只做协议这一层：

- `framing.rs`：`Content-Length` 帧的编解码。长度是**字节数**（中文消息比字符数长）。
- `protocol.rs`：编辑器需要的那一小块协议类型（位置、范围、诊断、补全项……）。
- `positions.rs`：字节偏移 ↔ LSP 位置的换算（UTF-16 列）。
- `lib.rs`：`Client`——起子进程、后台读线程、请求表、事件通道。

**没有引入第三方 LSP 库**：`lsp-types` 能省掉类型定义，但它的类型是给服务端用的
（`ServerCapabilities` 之外还有一大半客户端用不上的东西），而且"消息怎么收发"
终究要自己写——写了类型还得写一遍分发，反而多一层依赖。自己写这一层大约 600 行，
换来的是**依赖为零**和**行为完全可控**（比如服务器发来的请求统一回空结果）。

### 2. 客户端不阻塞 UI：握手在后台线程

语言服务器可能要好几天才起来（rust-analyzer 要加载整个工作区）。所以：

- `initialize` 的握手跑在**自己的线程**上，UI 线程不等它；
- 握手完成前打开的文档**先记下来**，握手结束时再发出去（带的是那时的文本）；
- 服务器发来的请求（`client/registerCapability`、`workspace/configuration` 等）
  一律回**空结果**，服务器就能继续做它的事；
- 服务器的诊断、补全走**事件通道**，UI 每帧 `drain` 一次。

UI 线程因此永远不等服务器。

### 3. 位置：UTF-16 列，换算只在 `lsp` crate 里做

协议默认按 UTF-16 code unit 数列（非基本平面的字符算 2 个）。`positions.rs` 提供
两个函数：`position_at`（字节 → 位置）和 `offset_at`（位置 → 字节）。

两个边界情况要有明确答案：

- **列超出行尾** → 落在行尾（服务器有时会问不存在的地方）；
- **列落在某个字符中间**（半个代理对）→ 落在那个字符的**开头**（位置只能在字符
  之间，不能在字符内部）。

`text` crate 不许知道 UTF-16 的事，换算只在 `lsp` 里做。

### 4. 同步方式按服务器声明的来，读不出来就发整篇

`initialize` 的回答里有 `textDocumentSync`，它可能是数字，也可能是
`{openClose, change, save}` 这样的对象。**这里踩过坑**：字段名在 JSON 里是
camelCase（`textDocumentSync`），Rust 字段是 snake_case——不写 `rename` 就永远读不到，
读不到就等于"按整篇同步处理"，而服务器要的是增量，**文档会被写坏**。

所以：

- **服务器要增量**（`change: 2`）→ 一次编辑发一条带 range 的 change；
- **服务器要整篇**（`change: 1`）→ 每次发整篇文本（不带 range）；
- **服务器没说** → 发整篇（不带 range 的 change 表示"整篇替换"，对任何服务器都
  是对的，而带 range 的 change 只对认 range 的服务器是对的）。

多编辑（多光标打字、"全部替换"）时**一次编辑的 range 算不准**——多处改动之后，
旧文本的坐标已经无从还原——所以多编辑一律发整篇。

### 5. `didChange` 的 range 是**改动前**的坐标

协议的 range 是改动**之前**文档里的位置。起点的坐标不受这次编辑影响（它前面的
文本没动），终点靠"被替换掉的旧文本"推进（`BufferChange.replaced` 里有那段旧文本，
`positions::advance` 按 UTF-16 推进）。

### 6. 位置换算用 `text` crate 的 rope，不拷全文

`positions::position_at` 用 `buffer.slice()` 取行首到某处的一段，`offset_at` 用
`buffer.line_text()`。两次都只碰一行，不拷全文。

### 7. 诊断：划线 + 状态栏计数

服务器发来的诊断是"位置 + 严重程度 + 文字"。平台层把位置换算成字节范围，画成
行下的横线（没有文字的诊断——少一个分号那种——画一小段）。状态栏显示
`✕ 错误数 ⚠ 警告数`，这样不用盯着屏幕也知道有没有问题。

### 8. 补全：Ctrl+Space 请求，列表浮在光标下

- `Ctrl+Space` 向服务器要当前位置的补全（winit 在 Windows 上把空格报成
  `NamedKey::Space`，两种说法都要认）；
- 回答里有几千项时，按**光标前的那个词**过滤；
- 列表浮在光标下面，放不下就翻到光标上面；
- `↑`/`↓` 选，`Enter`/`Tab` 采纳（把光标前那个词换成选中的文本），`Esc` 关掉，
  再按任何键则列表关掉、按键归编辑器。

### 9. 窗口要自己醒来听服务器说话

服务器在**自己的线程**上回答，窗口不会因为它有话要说就重绘。所以事件循环用
`ControlFlow::WaitUntil` 每 100 ms 醒一次（`about_to_wait`），把服务器的话收了
再决定要不要重绘。没有这个，诊断要等到用户敲键盘才会出现。

### 10. 假服务器 + 真服务器都验过

- `crates/lsp/src/bin/fake-lsp-server.rs`：一个会说话的假服务器，用来跑**端到端**
  测试（握手、didOpen、增量 didChange、补全），不依赖机器上装了什么；
- `crates/lsp/examples/real_server.rs`：对着**真的** rust-analyzer 跑一遍，把
  诊断和补全打出来。

验收脚本 `tools/window-check.ps1` 也多了一轮：编辑器带 `--lsp` 启动假服务器，
检查诊断的下划线确实画出来了（像素判据），以及补全列表确实出现了。

### 11. `--lsp` 与 `--complete` 两个开关

`--lsp <program>` 让调用者指定语言服务器（默认按语言选 `rust-analyzer`/`gopls`），
`--complete` 让编辑器启动时就请求一次补全。这两个开关是给**验收装置**用的：
合成按键按不出 Ctrl+Space（winit 读的是真实的修饰键状态），所以要有办法不靠
键盘就把列表请出来。

## 后果

- 诊断和补全在真窗口里能用：诊断画成下划线，状态栏有错误计数；Ctrl+Space 出
  补全列表，Enter 采纳。
- 和真 rust-analyzer 的握手、诊断、补全都验过（`examples/real_server.rs`）。
- 客户端不阻塞 UI：握手在后台，UI 每帧收一次消息。
- **依赖为零**：LSP 客户端没有引入第三方库。
- 已知缺口：
  - **跳转定义 / 引用 / 重命名 / 格式化**还没做。协议的请求通道
    （`Client::request`）已经在了，但还没接上界面。
  - 服务器发来的请求一律回空结果，所以 `workspace/configuration` 这类需要真实
    配置的服务器功能用不了。
  - rust-analyzer 在这台机器上是 rustup 代理，stable 工具链没装组件，直接跑会
    报"Unknown binary"；验收用的是工具链里的真二进制。
  - 多编辑一律发整篇文本，10MB 的文件一次多光标按键要传 10MB。

## 被否决的方案

- **引入 `lsp-types` / `tower-lsp`**：它们是给服务端写的框架；本编辑器要的只是
  "起进程、收发消息、算位置"，自己写更小更可控，还少一份依赖和一份许可证要记。
- **握手在 UI 线程上做**：服务器起来要几秒，窗口会白屏卡住。
- **不管服务器要什么，一律发增量 range**：服务器声明整篇同步时会把 range 当成
  整篇，**文档内容直接错乱**。反过来一律发整篇，对增量服务器是浪费但不会错——
  所以读不出来时选整篇。
- **多编辑时逐条发 range**：旧文本的坐标在多处改动后算不出来（要还原得先把整篇
  旧文本重建出来），宁可发整篇。
- **在 `text` crate 里做 UTF-16 换算**：文本模型不该知道协议的单位；换算属于
  `lsp`。
- **用 `buffer.text()` 换算位置**：一次按键拷 100MB；用 rope 的分块取。
- **补全列表跟着输入实时过滤**：要每敲一个键就重新请求，延迟高、请求多。第一版
  是"请求一次 → 过滤一次 → 采纳"，输入即关闭。
- **在事件循环里轮询服务器**：winit 没有"数据可读"的回调，只能定时醒（每 100 ms）。
- **把语言服务器的进程交给 UI 层管**：违反架构约束（UI 不启动进程）。
