# ADR-0008：查找替换建在多光标地基上，搜索是分块的

- 状态：已接受
- 日期：2026-11-12
- 适用范围：`editor/crates/text`、`editor/crates/editor-core`、`editor/crates/platform`

## 背景

计划 §5.1 的 MVP 清单里有"查找替换"。它看着是一个小功能，实际上要回答三个问题：

1. **搜索怎么做**：文档可能有几百 MB，搜索不能把全文拷进内存；
2. **多处替换怎么落地**：一次改几十处，在撤销历史里应该是一步；
3. **匹配怎么和编辑器交互**：哪些匹配高亮、当前匹配是哪个、"全选匹配"之后怎么编辑。

第 2 个问题在 ADR-0007 之后已经有了答案（一次事务里的多个编辑），所以这一条
ADR 讲的是**搜索**与**交互**这两件事。

## 决策

### 1. 搜索在 rope 的分块上做，窗口保留上一块的尾巴

`Buffer::find_all(query, case_sensitive)` 遍历 `rope.chunks()`，逐块扫描，**从不
把全文拷进内存**。跨块的匹配靠一个"窗口"找到：窗口保留上一块的尾巴
（`needle.len() - 1` 字节），所以跨边界的匹配不会漏。

扫描算法抽成了自由函数 `find_all_in_chunks`，它只认"一串字节块"——于是**跨块的
行为可以用单元测试钉死**，不必真的造一个几百 MB 的 rope 也不必依赖 ropey 的
内部切分策略。

两条不变量：

- **匹配不重叠**：下一个匹配从上一个匹配的结尾开始。按重叠的匹配去算替换，
  会把同一段文字写两遍。
- **大小写折叠只看 ASCII**：非 ASCII 字母折叠后字节数会变，匹配长度就对不上了。

### 2. "全选匹配"就是把匹配变成选区

`Editor::set_selection_ranges(&[Range])` 把一组范围变成一组选区。于是：

- `Alt`+`Enter`（全选匹配）= 匹配变成选区 = 用户随后的一次输入同时改所有匹配；
- `Ctrl`+`Alt`+`Enter`（全部替换）= `Editor::replace_ranges` 一次事务改所有匹配，
  撤销**一次**全部回去。

查找条没有自己的一套"多处编辑"逻辑，它用的是编辑器本来的多光标模型。

### 3. 查找条是 platform 层的一个小部件

`platform/src/find.rs` 里的 `FindBar` 只持有：查询词、替换词、当前字段、是否区分
大小写、匹配列表、当前是哪个匹配。**文本本身留在 `editor-core`**，查找条只
知道匹配在哪儿。

查找条打开时，编辑器当前选中的文本会成为查询词——用户最可能在找的就是刚选中的
那几行。

### 4. 交互

| 操作 | 效果 |
|---|---|
| `Ctrl`+`F` | 打开查找条 |
| `Ctrl`+`H` | 打开查找条（带替换框） |
| 输入 / 退格 | 改查询词（或替换词），实时搜索 |
| `Tab` | 在查询词与替换词之间切换 |
| `Enter` / `Shift`+`Enter` | 下一个 / 上一个匹配 |
| `Alt`+`Enter` | 全选匹配（变成多光标） |
| `Ctrl`+`Alt`+`Enter` | 全部替换 |
| `Esc` | 关闭查找条，键盘还给编辑器 |

查找条打开时，键盘归查找条：字符进查询框，IME 的合成结果也进查询框，不进文档。

### 5. 绘制

- 正文里，所有匹配画一层暗黄底色，**当前匹配**画一层亮黄底色；
- 匹配底色画在**选区底下**（`EditorView::draw` 先画匹配、再画选区），这样用户
  自己的选区仍然压得住匹配；
- 查找条画在正文右上角，浮在文字之上（和 VS Code 一样）。

### 6. 浮在正文上的部件，正文要让开

渲染器是**先画所有色块、再画所有文字**：字形在色块之后画。所以查找条这种浮在
正文上的部件，如果直接画，正文的字会**透过来**（字画在查找条的底色上面）。

真正的分层（浮层之上还能有字）要改渲染管线：字形顶点在一个缓冲里，分两次画就
会互相覆盖（`queue.write_buffer` 在提交前就生效了）。代价太大，不划算。

所以这里换了个办法：**正文不在浮层底下画字**。`EditorView::draw` 收一个
`FindOverlay`，里面是浮层的位置；凡是横向经过浮层的行，它的字就**停在浮层的
左边**（查找条靠在正文右边缘，所以被盖住的部分正好就是该被盖住的部分）。

浮层的宽度是 `min(420, 正文宽度)`，所以正文太窄时浮层会占满整个正文——那
时候正文就只剩下一行字，这是可以接受的（正文本来就窄）。

### 7. 验收装置：三个坑

`tools/window-check.ps1` 验的是真窗口。这次为了验查找条，撞到三个坑，都值得
记下来：

1. **winit 的修饰键读的是真实键盘状态**（`GetKeyState`），所以 posted 的
   `WM_KEYDOWN` 不会让 winit 以为按住了 Ctrl——`Ctrl`+`F` **无法**用合成消息
   触发（`SendInput` 需要抢前台窗口，不适合放在验收装置里）。所以编辑器加了
   `--find <文字>`：启动时就把查找条打开并搜索。查找条的**按键**由单元测试
   覆盖，查找条的**画面**由真窗口装置覆盖。
2. **脚本默认不是 DPI-aware 的**：系统给它的是"系统缩放空间"的坐标，于是
   `SetWindowPos`/`GetClientRect` 说的尺寸和窗口真正的尺寸差一个缩放因子——
   窗口**其实从来没被改过大小**，画面也被裁掉了一块。脚本现在先问系统自己是
   不是 aware，不是就把每个测量都换算成物理像素。
3. **真实鼠标会和 posted 消息打架**：鼠标停在窗口上时，它自己的
   `WM_MOUSEMOVE` 排在 posted 的后面，编辑器就跟着真鼠标走，装置变成一场
   竞态（同一个脚本一会儿过一会儿不过）。装置现在先把真鼠标挪到窗口外，并且
   **检查**它确实不在窗口里——是就报错，而不是看运气。

判据本身也修了：原来查的是"蓝色像素够不够多"，量到的其实是正文左侧那道蓝边
（坐标没乘缩放因子，量错了地方），而且状态栏的灰字也算"蓝"。现在查的是**具体
颜色**（选区蓝、强调蓝、匹配黄），并且每个判据都有一张"应该为 0"的对照图：
没有拖拽就没有选区色，没有搜索就没有匹配色，没有打开查找条就没有强调色。

## 后果

- 查找替换可用：查找、逐个替换、全部替换、全选匹配后一起编辑。
- 全部替换是撤销历史里的**一步**。
- 搜索不拷贝全文：100MB 文档的搜索内存占用是窗口大小（几 KB），不是文档大小。
- 查找条打开时，**编辑器自己的选区不动**——匹配用底色表示，当前匹配用更亮的
  底色表示。只有"全选匹配"才会去改选区，因为那正是它的意思。
- **匹配高亮只画在可见的行上**：`selection_rects` 只遍历布局里已有的行，所以
  滚动时不需要重算高亮。
- 搜索是**全量**的：每次改查询词都会重新扫一遍全文。大文档上这会卡——
  下一步是"从光标处增量搜索"（先扫可见范围，再按需往后）。
- 查找条**浮在正文上**，而渲染器没有分层，所以正文要在浮层底下让开
  （见 §5.6）。真正的分层是渲染器该有的能力，不在这次的范围里。
- `Ctrl`+`F` **无法**用合成键盘消息触发（winit 读真实键盘状态），所以编辑器
  带了 `--find <文字>`：启动时就把查找条打开并搜索。这既是给用户的一个
  小功能，也是让验收装置能看见查找条的办法。

## 被否决的方案

- **把全文拷出来再搜**（`buffer.text()` + `str::find`）：100MB 文档要拷 100MB，
  而且每次改查询词都拷一次。分块扫描没有这个问题。
- **让匹配可以重叠**：搜索 "aa" 在 "aaaa" 里给出 0..2 和 1..3，替换时第二处会覆盖
  第一处的结果，文字被写坏。非重叠是替换正确的前提。
- **在查找条里自己实现"多处替换"**：那等于把多光标模型又实现一遍，而且两套模型
  会对不上（撤销步数、光标位置）。查找条复用 `Editor::replace_ranges`。
- **查找条打开时把匹配做成编辑器选区**：这样每敲一个字符就会丢掉用户原来的选区，
  而且"当前匹配"和"选区"会互相打架——用户在正文里点一下，查找条就不知道该高亮
  哪个了。用底色表示匹配更干净。
- **大小写折叠用 `to_lowercase()`**：非 ASCII 字母折叠后字节数会变（`İ` 之类），
  匹配长度就对不上原文。用 ASCII 折叠，规则简单且长度守恒。
- **查找条做成独立 crate**：它只有几百行，且完全依赖 `editor-core` 的选区模型，
  独立成 crate 只会多一层依赖。
- **改渲染器做真分层**：字形顶点在一个缓冲里，分两段画会互相覆盖；要分层就得
  换字形渲染的后端（或者维护两个顶点缓冲），代价远大于这次的收益。改成"正文
  在浮层底下让开"，效果一样，代码少得多。
