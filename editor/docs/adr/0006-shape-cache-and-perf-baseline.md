# ADR-0006：整形结果按文本缓存，性能基线进 CI

- 状态：已接受
- 日期：2026-11-12
- 适用范围：`editor/crates/render`、`editor/crates/platform`

## 背景

ADR-0005 把正文区域做成了真正的编辑器，也带来一个性能问题：一次按键要先花
**11.6ms** 在"还没碰 GPU"的文字工作上，而计划 §9 给"按键到画面更新"的整条预算
是 P95 < 16ms。也就是说，一半以上的帧预算被文字吃掉了。

测量（`crates/render/examples/shaper_probe.rs`）显示整形本身很贵：

- 一次整形的固定开销约 10~20µs；
- 每个字符约 5~9µs——31 字符的一行要 160~280µs；
- `Shaping::Advanced`（带字体回退）比 `Shaping::Basic` 慢 2~3 倍，回退机制是
  主要开销。

而**同一段文字每帧被整形了两次**：布局量一次（要整条逻辑行的宽度来决定在哪
折行），绘制再整一次（要的是折行之后的每一段）。两者的职责不同，所以这份重复
不是靠改调用点能消掉的，只能缓存。

顺带查出一个真 bug：`LayoutRun::line_w` 是**整行**的宽度，而一行会按字种
（script）拆成多个 run，每个 run 都报告同一个整行宽度。原先的实现把每个 run
的 `line_w` 相加，于是中英混排的一行宽度被算成**两倍**——这类行会提前一半
折行，中文越多偏得越厉害。

## 决策

### 1. 整形结果按（文本, 字号, 行高, 字族, 绘制尺寸）缓存

`TextShaper` 持有 `ShapeCache`：

- **键**：文本 + 字号 + 行高 + 字族 + 绘制尺寸（宽高可缺省）；
- **值**：整形好的 cosmic-text `Buffer` + 每个字节边界的 x 偏移 + 宽度；
- **容量** 2048 条，满了淘汰最久没用过的那条（用使用计数器比较的 LRU）。

测量与绘制共用同一个 `TextShaper`，也就是同一个字体系统与同一份缓存。

### 2. 绘制复用缓存里的 buffer

`Renderer::prepare_text` 不再每帧新建 `Buffer`，而是向缓存要整形结果，取它的
`Buffer` 交给 glyphon 的 `TextArea`。整形好的 `Buffer` 里连排版结果都留着，
所以每帧只剩遍历 run 的开销，字形本身由 atlas 缓存。

### 3. 宽度取最大值，不求和

`run.line_w` 是整行宽度，所以多 run 的行取最大值才是这一行的宽度。

### 4. 性能基线做成基准 + 阈值门禁

`crates/platform/benches/editor_frame.rs` 用手写 harness（不用 criterion：本机
MSVC 的 C 工具链是坏的，criterion 依赖 `alloca`）。

每个用例测两遍：

- **cold**：清空缓存后测——滚到从未整形过的文本时的代价；
- **warm**：缓存热着测——打字的代价（只有被改的那一行需要重新整形）。

超过预算就 `exit(1)`，回归会被 CI 挡住。计划 §9 要求"每个性能目标必须配套
benchmark，性能回归超阈值阻止合并"，这条门禁就是它的落点。

## 后果

实测（release，10000 行文档，视口宽 900，40 行可见）：

| 用例 | 缓存前 p95 | 缓存后 p95（warm） |
|---|---|---|
| 布局 40 行 | 8.03 ms | 0.086 ms |
| 布局 200 行 | 28.09 ms | 0.515 ms |
| 一帧的文字工作（布局 + 绘制） | 15.24 ms | 0.106 ms |
| 命中测试 | 0.001 ms | 0.001 ms |
| 光标所在行查找 | 0.000 ms | 0.000 ms |

- 打字一帧的文字工作从 11.6ms 降到 0.1ms，帧预算的七成被释放出来；
- **冷路径仍然是 19ms 一帧**（滚到没整形过的文本），超过 §9 的 16ms。这是
  **增量布局**要解决的事，已记为待办；
- 缓存占用与可见行数成正比（几千行 ≈ 几 MB）；
- 字号或字族变了，缓存里的整形会整体作废——键里带了尺寸，所以不会画错，
  只是白整形一次。

## 被否决的方案

- **打开 cosmic-text 的 `shape-run-cache` feature**：它的键是（文本, 属性），
  **不含字号**——同一段文字换字号会拿到上一个字号的字形。宁可自己缓存。
- **按字符宽度估算布局**（等宽字体里每个字符一个 advance）：快，但中文会落到
  别的字体上，advance 不一样，光标就会偏。与 ADR-0005 否决的是同一条理由。
- **让 `ui` 层缓存字形**：`ui` 不依赖 `render`，字形是渲染器的东西。缓存放在
  渲染器里，测量与绘制才能共用同一份整形结果。
- **只缓存测量结果，绘制照旧每帧整形**：稳态下绘制仍然要 7ms，省不下来。
- **把整形放到后台线程**：要先解决"整形结果什么时候才能安全交给渲染线程"的
  顺序问题。当前 0.1ms 的热路径不值得引入这个复杂度。
